# EQTransformer — Высокопроизводительный пайплайн обработки сейсмических данных

> Форк [smousavi05/EQTransformer](https://github.com/smousavi05/EQTransformer) для автоматической обработки непрерывных записей региональной сейсмической сети: от обнаружения P/S-вступлений до определения параметров событий и формирования бюллетеня.

---

## Обзор

Проект объединяет нейросетевую детекцию EQTransformer, многостанционную ассоциацию двумя независимыми поисками, оценку локальной магнитуды, определение гипоцентров LOCSAT с региональными скоростными моделями и отсев событий по признакам пиков, решения и истории станций. Выходной бюллетень IMS1.0:SHORT сопоставляется с официальными бюллетенями ФИЦ ЕГС РАН.

Данный форк расширяет оригинальный EQTransformer (EQT) полностью **in-memory, GPU-ускоренным пайплайном**, который заменяет дисковую HDF5-архитектуру. В историческом замере один месяц данных с одной станции обрабатывался за **~20 минут** вместо ~12 часов — ускорение примерно в **35 раз**. Проверка на исторических данных подтвердила сохранение точности детекции при переходе к in-memory обработке.

Конвейер применяется к данным региональной сети Северного Кавказа. CPU- и GPU-обёртки позволяют распределять обработку станций между процессами; выбранная конфигурация учитывает разрывы записи и использует MC Dropout для оценки неопределённости. Архитектура, алгоритмы и последовательность запуска описаны в [технической документации](docs/doc-technical.md).

## Схема конвейера

```text
Архив miniSEED и метаданные станций
  → подготовка данных
  → детекция P/S и оценка неопределённости
  → ассоциация двумя поисками
  → ML и отбор станций
  → окончательная дедупликация
  → LOCSAT и региональное уточнение
  → отсев событий
  → бюллетень IMS1.0:SHORT
  → сравнение с эталоном
```

Между стадиями сохраняются пики, магнитуды и идентификаторы событий. Для LOCSAT отдельно подготавливается набор согласованных вступлений; результаты локации связываются с основным набором событий по ID.

## Ключевые улучшения

### 1. In-Memory пайплайн

Оригинальный EQT записывает предобработанные данные в HDF5-файлы на диск, затем читает их обратно для инференса. На наборах данных масштаба месяца это создаёт серьёзное I/O-узкое место.

Предобработка и инференс передают данные через оперативную память, без промежуточных HDF5-файлов:

```
miniSEED → ObsPy → сегменты записи → preprocessorV7_mem() → predictor_mem_non_hdf_load_model_v6() → CSV
```

- `preprocessorV7_mem()` подготавливает массивы в памяти и приводит записи к 100 Гц через `st.resample()`.
- `predictor_mem_non_hdf_load_model_v6()` принимает подготовленные массивы и возвращает результаты детекции и определения P/S-вступлений.
- В выбранном режиме `--gap-mode merge` генератор `geofile_splitter_multi_chanels_v4()` объединяет фрагменты каналов и выдаёт 10-минутные сегменты с шагом 5 минут. Это позволяет продолжать обработку записи после разрывов, на которых прежний режим ограничивал диапазон обработки.

Волновые формы читаются группами файлов, а сегменты последовательно передаются в обработку: загружать весь месячный архив в память не требуется. Исходный поток ObsPy сохраняется до завершения обработки его сегментов, поскольку `slice()` возвращает представления исходных данных.

| Метрика | Оригинал | Данный форк |
|---|---|---|
| Модель I/O | HDF5 на диск | In-memory |
| Время обработки / месяц (SOC) | ~12 часов | **~20 минут** |
| Ускорение | 1× | **~35×** |

### 2. Активация cuDNN для LSTM-слоёв

Рекуррентная часть рабочей модели EQT включает два двунаправленных и два однонаправленных LSTM-блока — шесть LSTM-ячеек. Исходный `recurrent_dropout=0.2` препятствует выбору ускоренного cuDNN-пути.

Для GPU-выполнения загрузчик `load_model_cudnn_v2()` (`core/detector.py`) патчит модель **in-place после загрузки**, сохраняя обученные матрицы весов и структуру сети:

```python
# recurrent_dropout и implementation — read-only @property на уровне слоя LSTM.
# Изменяемые значения живут в lstm.cell.
lstm.cell.recurrent_dropout = 0.0
lstm.cell.implementation = 2
```

Для `Bidirectional`-слоёв патчатся оба направления — `forward_layer.cell` и `backward_layer.cell`.

**Результат:** в рабочей GPU-конфигурации LSTM выполняются через ускоренные cuDNN-ядра. CPU-обёртка использует тот же загрузчик, но выполняет модель на CPU.

---

### 3. Оптимальное батчирование предсказаний

Отдельный вызов модели для каждого 60-секундного окна создаёт накладные расходы. В этом форке окна сегмента объединяются и передаются модели батчами.

При MC Dropout батчами обрабатываются также стохастические копии окон. Число вызовов зависит от размера батча и числа копий; обработка сегмента не ограничивается одним вызовом.

Историческое сравнение обработки одной станции:

| Стратегия | Вызовов / месяц | Время выполнения |
|---|---|---|
| На каждое 60-с окно | ~87 000 | ~8.5 часов |
| Окна сегмента вместе (13 окон, без MC-копий) | ~8 150 | **~20 минут** |

---

### 4. Реальный MC Dropout для оценки неопределённости

Dropout-слои Keras по умолчанию отключены во время инференса (`model.predict()`) — это касалось и первой версии пайплайна: `estimate_uncertainty=True` был лишь флагом, не менявшим поведение по сути, и всегда давал нулевую неопределённость (std≈0).

Сейчас реализован настоящий Monte Carlo Dropout: `predictor_mem_non_hdf_load_model_v6()` (`core/detector.py::worker_v4`) вызывает `model(batch, training=True)` — dropout остаётся активным, несколько проходов (`number_of_sampling`) дают разброс предсказаний, откуда и берётся содержательная оценка `detection_uncertainty`/`p_uncertainty`/`s_uncertainty`. Эта оценка затем используется на этапе ассоциации (см. ниже) — не просто печатается для справки.

---

### 5. Параллельная многостанционная обработка

Для одновременной обработки нескольких станций реализованы CPU- и GPU-обёртки над общим детектором. В выбранном режиме `--gap-mode merge` обе используют `core/detector.py::process_station_v4()`.

#### `core/cpu_pipeline.py` / `core/gpu_pipeline.py`

Оба поднимают `ProcessPoolExecutor` с `initializer`: каждый рабочий процесс загружает модель (`load_model_cudnn_v2`) **один раз**, после чего обрабатывает назначенные ему станции. CPU-версия скрывает GPU (`set_visible_devices([], 'GPU')`) и ограничивает TF-потоки на воркер, чтобы процессы не конкурировали за ядра; GPU-версия настраивает `memory_growth` и упирается в объём VRAM, а не в число ядер CPU. Список станций, диапазон дат и число воркеров задаются флагами (`--help` на каждом даёт полный список).

```bash
conda activate eqt3
python core/gpu_pipeline.py \
  --stations SOC,VSLR,BEYR \
  --date-from 2024-04-01 --date-to 2024-05-01 \
  --gap-mode merge \
  --estimate-uncertainty --number-of-sampling 5 \
  --max-workers 2
```

Число воркеров в примере условное: каждый GPU-процесс хранит собственную модель и рабочие массивы, поэтому его подбирают под доступную VRAM и производительность. Для CPU используется `core/cpu_pipeline.py` с теми же параметрами периода, станций и детекции; число процессов и TF-потоков на процесс задаются через `--max-workers` и `--tf-threads-per-worker`.

Оценку неопределённости и пять MC-копий задаём явно: у CPU-обёртки оценка по умолчанию выключена, а число копий равно 10.

Подробности механики (в т.ч. известная особенность — общий лог `processing_log.csv`, который при параллельной обработке сохраняет данные только последней завершившейся станции) — `core/cpu_pipeline.md`, `core/gpu_pipeline.md`.

`core/detector.py`, вызываемый напрямую (`python core/detector.py --stations ...`), обрабатывает свой список станций **последовательно, одним процессом** — для параллельной обработки нескольких станций нужен один из `cpu_pipeline.py`/`gpu_pipeline.py` (см. `core/detector.md`).

## Многостанционная ассоциация событий

После станционной детекции пики объединяются в сетевые события. Выбранный ассоциатор `run_associator_v3()` выполняет два независимых поиска по одному набору детекций: времена вступлений проверяются на согласованность с пробным положением эпицентра и временем очага по годографу IASP91.

- **Первичный поиск** формирует основные гипотезы событий.
- **Альтернативный поиск** сохраняет другие варианты P-вступлений той же станции и дополнительно проверяет совместимость поддерживающей S с её P. Это позволяет получить гипотезы, которые первичный поиск мог пропустить при исключении уже использованных детекций.
- Для принятия гипотезы нужны не менее **шести P-станций**; согласованные S повышают её поддержку.

До поиска `core/associator.py` подготавливает стейджинг с отбором по вероятностям и настройками SNR и неопределённости. В выбранном режиме `--uncertainty-mode weight` вероятности корректируются с учётом MC Dropout-неопределённости; само голосование ассоциатора использует времена вступлений и число разных станций.

Результаты объединяются в два этапа. **До ML** удаляются только полностью одинаковые наборы станций и P/S-вступлений. Близкие альтернативы сохраняются: различия в пиках могут изменить отбор станций, расстояния и итоговую магнитуду.

**После ML** выполняется окончательная дедупликация с приоритетом первого поиска: дублями считаются гипотезы с не менее чем четырьмя точными совпадениями «станция, время P» и разностью расчётных времён очага не более 10 с. Для оставленных событий сохраняются исходные идентификаторы; основной XML и отдельный вход LOCSAT согласуются по этим ID.

Алгоритм и последовательность запуска описаны в [технической документации](docs/doc-technical.md#6-модуль-ассоциации-coreassociatorpy). Оконный `run_associator_v2()` остаётся альтернативным вариантом; секторный ассоциатор перенесён в `legacy/`.

## Фильтрация по локальной магнитуде (ML)

После ассоциации `core/ml_filter_v5.py` оценивает **локальную магнитуду ML** по амплитудам смещения после снятия инструментального отклика и расстояниям до станций. Используется формула Дягилева и др. (2023), разработанная для Терско-Каспийского прогиба; выбранный порог сохранения события — **ML ≥ 1.5**.

Важная часть расчёта — отбор станций события. Ассоциация может включать посторонние пики, а ошибочно короткий интервал S−P занижает расстояние и станционную ML. В режиме **`p-traveltime`** собственная группа станций определяется по согласованности времён P с годографом и подтверждается по S−P. Если подтверждения недостаточно, используются резервные режимы расчёта. Итоговая ML получается усреднением допустимых станционных оценок после отсечения выбросов.

Шаг формирует два связанных выхода:

- **Основной XML** — события, прошедшие порог, с ML события и станций (`--write-ml`).
- **Отдельный ptt-XML** — отобранные P и согласованные S со стартовой точкой для LOCSAT (`--out-xml-ptt`). Его состав пиков может отличаться от использованного для ML; связь сохраняется по ID событий.

Станционные поправки при необходимости подготавливаются отдельно через `core/sta_correction_estimator.py`. Для каждого запуска ассоциатора используется новый кэш амплитуд; экспорт получает рассчитанную ML из основного XML.

Формула, измерение амплитуд и правила отбора описаны в [технической документации](docs/doc-technical.md), §8. Подробности инструментов — в `core/ml_filter_v5.md` и `core/sta_correction_estimator.md`.

## Локация, отсев событий и экспорт бюллетеня

После ML и окончательной дедупликации конвейер определяет параметры очага, выполняет дополнительный отсев событий и формирует выходной бюллетень:

- **Локация — `core/locator.py`.** LOCSAT в SeisComP рассчитывает широту, долготу, глубину и время очага по отобранным вступлениям. Сначала получается решение IASP91, затем по его координатам выбирается региональная скоростная модель. Для Северного Кавказа подготовлены таблицы для **16 моделей НИИ**. Региональное решение уточняется от исходного; вне заданных областей или при несходимости уточнения сохраняется IASP91.
- **Отсев событий — `core/false_event_filter.py`.** Логистическая модель использует **17 признаков**: характеристики пиков, разброс станционных ML, параметры решения LOCSAT и историю активности станций за предыдущие семь суток. Отсев сокращает автоматическую выдачу; сохранённые события сохраняют исходные пики, магнитуды и идентификаторы.
- **Экспорт — `core/export_bul.py`.** Формируется бюллетень **IMS1.0:SHORT** с P/S-вступлениями, координатами, глубиной, магнитудами и амплитудами. В выбранном режиме `--locator-mode enrich` координаты добавляются из LOCSAT, а `--ml-from-xml` сохраняет ML основного расчёта. Время очага в BUL остаётся экспортной оценкой по S−P; невязки вступлений относятся к решению LOCSAT.

Качество проверяется через **`core/compare_bul.py`** по официальным бюллетеням ФИЦ ЕГС РАН: для эталона используется MPVA ≥ 1.5, совпадение требует не менее четырёх общих станций и близости времени очага в пределах ±60 или ±10 с. При наличии координат дополнительно оцениваются ошибки эпицентра и глубины.

`core/validate_associator_v2.py` остаётся диагностическим инструментом и библиотекой S−P-расчётов для экспорта; его отдельный запуск не является обязательной стадией конвейера.

Подробности локации, отсева и экспорта — в [технической документации](docs/doc-technical.md), §8б–9; интерфейсы модулей — в `core/locator.md`, `core/export_bul.md` и `core/compare_bul.md`.

## Возможные направления улучшения

- **Автоматическая обработка поступающих данных.** Оркестратор подготовки данных, детекции и ассоциации с запуском по расписанию или по мере пополнения архива. Для этого требуется определить момент готовности файлов и правила обработки запаздывающих станций.
- **Учёт состояния и восстановление после сбоев.** Хранение отметок об обработанных станциях и интервалах, продолжение прерванного запуска и управляемый пересчёт при поступлении дополненных данных.
- **Единая конфигурация запуска.** Общий профиль путей, станций, периода и параметров стадий поверх существующего CLI; параметризация подготовки данных, которая пока настраивается в исходных файлах.
- **Мониторинг автоматических запусков.** Сводный статус стадий, контроль полноты данных и уведомления об ошибках для работы без постоянного наблюдения за терминалом.
- **Дообучение на региональных данных.** Адаптация EQTransformer к кавказским записям с отдельной проверкой влияния на детекцию и точность P/S-вступлений.

## Установка

### Детекция и обработка данных

Рабочее окружение Windows использует Python 3.10, TensorFlow GPU 2.10 и Keras 2.10. Основные версии, зафиксированные в установленном окружении `eqt3`:

| Компонент | Версия |
|---|---|
| Python | 3.10.8 |
| tensorflow-gpu / Keras | 2.10.0 / 2.10.0 |
| NumPy / SciPy | 1.26.4 / 1.15.2 |
| h5py | 3.9.0 |
| CUDA Toolkit / cuDNN | 11.2 / 8.1 |

Базовые команды подготовки окружения:

```bash
conda create -n eqt3 python=3.10.8 pip
conda activate eqt3
conda install -c conda-forge cudatoolkit=11.2 cudnn=8.1.0
python -m pip install "tensorflow-gpu==2.10.0" "keras==2.10.0" "protobuf==3.19.6"
python -m pip install "numpy==1.26.4" "scipy==1.15.2" "h5py==3.9.0"
python -m pip install obspy pandas matplotlib tqdm scikit-learn openpyxl
```

TensorFlow устанавливается через pip. Для GPU в Windows библиотеки CUDA/cuDNN должны быть доступны через `PATH`, включая каталог `Library/bin` активного conda-окружения. Ограничения GPU-поддержки Windows описаны в [инструкции TensorFlow](https://www.tensorflow.org/install/pip#windows-native).

### Локация LOCSAT

Для определения гипоцентров нужна отдельная установка **SeisComP**; в рабочей конфигурации она используется через WSL. Модуль `seiscomp` не входит в conda-окружение `eqt3`: LOCSAT запускается через `seiscomp exec seiscomp-python`.

Перед запуском подготавливаются SC3ML-инвентарь станций для обрабатываемого периода и таблицы годографов. Региональные модели LOCSAT используют собственные каталоги таблиц; CSV-годографы ассоциатора и ML задаются отдельно.

Для обработки также нужны веса EQTransformer, волновые записи miniSEED и метаданные станций. Форматы входов и последовательность запуска описаны в [технической документации](docs/doc-technical.md), §3 и §11.
