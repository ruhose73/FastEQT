# EQTransformer — Высокопроизводительный пайплайн обработки сейсмических данных

> Форк [smousavi05/EQTransformer](https://github.com/smousavi05/EQTransformer) с полностью переработанным пайплайном для продакшн-масштабного непрерывного мониторинга сейсмичности.

---

## Обзор

Данный форк расширяет оригинальный EQTransformer (EQT) полностью **in-memory, GPU-ускоренным пайплайном**, который заменяет дисковую HDF5-архитектуру. Результат — ускорение обработки примерно в **35 раз**: один месяц данных с одной станции обрабатывается за **~20 минут** вместо ~12 часов при полном сохранении точности детекции.

Система работает на региональной сейсмической сети района Сочи (Северный Кавказ, Россия). Изначально протестирована на 12 станциях (январь 2024, эталонный каталог 49 событий) — с тех пор расширена до **~60 станций** и нескольких обработанных месяцев 2024 года, с добавлением фильтрации по локальной магнитуде и сравнения с официальными бюллетенями. Подробный, поддерживаемый в актуальном состоянии разбор каждого модуля — в `core/README.md` (и связанных `core/*.md`); этот файл — общий обзор архитектуры и мотивации решений.

## Ключевые улучшения

### 1. In-Memory пайплайн

Оригинальный EQT записывает предобработанные данные в HDF5-файлы на диск, затем читает их обратно для инференса. На наборах данных масштаба месяца это создаёт серьёзное I/O-узкое место.

Новый пайплайн полностью исключает диск из цикла обработки:

```
SEED-файлы → ObsPy (RAM) → preprocessorV6_mem/V7_mem() → model.predict()/model() → строки CSV
```

- `preprocessorV6_mem()`/`preprocessorV7_mem()` возвращают Python-словари вместо записи в HDF5 (V7 дополнительно делает корректный ресемплинг через `st.resample()`, а не растяжение массива)
- `predictor_mem_non_hdf_load_model_v4/v6()` принимают массивы напрямую из памяти и возвращают строки результатов без записи в файл
- Генератор `geofile_splitter_multi_chanels_v2/v3()` выдаёт по одному 10-минутному сегменту за раз (шаг 5 минут, 50% перекрытие) — RAM остаётся ограниченным независимо от длины набора данных

Потребление памяти стабильно: каждый сегмент удаляется после обработки, дневной поток ObsPy освобождается только после того, как все его сегменты обработаны (важный нюанс: ObsPy `slice()` возвращает представления, поэтому поток должен оставаться живым до завершения генератора).

| Метрика | Оригинал | Данный форк |
|---|---|---|
| Модель I/O | HDF5 на диск | In-memory |
| Время обработки / месяц (SOC) | ~12 часов | **~20 минут** |
| Ускорение | 1× | **~35×** |

### 2. Активация cuDNN для LSTM-слоёв

Модель EQT содержит 4 LSTM-слоя, обученные с `recurrent_dropout=0.2` и `implementation=1`. Оба параметра блокируют cuDNN, заставляя TensorFlow использовать медленную обобщённую CUDA-реализацию.

Оригинальный EQT не предоставляет механизма для исправления этого. Данный форк патчит модель **in-place после загрузки**, не затрагивая сохранённые веса и архитектуру:

```python
# recurrent_dropout и implementation — read-only @property на уровне слоя LSTM.
# Изменяемые значения живут в lstm.cell.
lstm.cell.recurrent_dropout = 0.0
lstm.cell.implementation = 2
```

Для `Bidirectional`-слоёв патчатся оба направления — `forward_layer.cell` и `backward_layer.cell`. Всего 6 ячеек. Патч прозрачен для всего последующего кода и реализован в `load_model_cudnn_v2()` (`core/detector.py`).

**Результат:** `model.predict()`/`model()` работает с cuDNN LSTM-ядрами, что подтверждается записью `Loaded cuDNN version 8100` в логах TF.

---

### 3. Оптимальное батчирование предсказаний

TensorFlow имеет фиксированные накладные расходы ~0.3 с на каждый вызов `model.predict()`. Оригинальный пайплайн вызывает predict для каждого 60-секундного окна отдельно.

Новый пайплайн батчирует все окна 10-минутного сегмента в один вызов:

| Стратегия | Вызовов / месяц | Время выполнения |
|---|---|---|
| На каждое 60-с окно | ~87 000 | ~8.5 часов |
| На 10-мин сегмент (13 окон) | ~8 150 | **~20 минут** |

---

### 4. Реальный MC Dropout для оценки неопределённости

Dropout-слои Keras по умолчанию отключены во время инференса (`model.predict()`) — это касалось и первой версии пайплайна: `estimate_uncertainty=True` был лишь флагом, не менявшим поведение по сути, и всегда давал нулевую неопределённость (std≈0).

Сейчас реализован настоящий Monte Carlo Dropout: `predictor_mem_non_hdf_load_model_v6()` (`core/detector.py::worker_v4`) вызывает `model(batch, training=True)` — dropout остаётся активным, несколько проходов (`number_of_sampling`) дают разброс предсказаний, откуда и берётся содержательная оценка `detection_uncertainty`/`p_uncertainty`/`s_uncertainty`. Эта оценка затем используется на этапе ассоциации (см. ниже) — не просто печатается для справки.

---

### 5. Параллельная многостанционная обработка

Для одновременной обработки нескольких станций реализовано два независимых механизма параллелизма — не альтернативные пайплайны, а обёртки над одним и тем же `core/detector.py::process_station_v3()`.

#### `core/cpu_pipeline.py` / `core/gpu_pipeline.py`

Оба поднимают `ProcessPoolExecutor` с `initializer`: каждый рабочий процесс загружает модель (`load_model_cudnn_v2`) **один раз**, после чего обрабатывает назначенные ему станции. CPU-версия скрывает GPU (`set_visible_devices([], 'GPU')`) и ограничивает TF-потоки на воркер, чтобы процессы не конкурировали за ядра; GPU-версия настраивает `memory_growth` и упирается в объём VRAM, а не в число ядер CPU. Список станций, диапазон дат и число воркеров задаются флагами (`--help` на каждом даёт полный список).

```bash
conda activate eqt3
python core/gpu_pipeline.py --stations SOC,VSLR,BEYR --date-from 2024-04-01 --date-to 2024-05-01 --max-workers 6
# или: python core/cpu_pipeline.py ...
```

Подробности механики (в т.ч. известная особенность — общий лог `processing_log.csv`, который при параллельной обработке сохраняет данные только последней завершившейся станции) — `core/cpu_pipeline.md`, `core/gpu_pipeline.md`.

`core/detector.py`, вызываемый напрямую (`python core/detector.py --stations ...`), обрабатывает свой список станций **последовательно, одним процессом** — для параллельной обработки нескольких станций нужен один из `cpu_pipeline.py`/`gpu_pipeline.py` (см. `core/detector.md`).

## Многостанционная ассоциация событий

После детекции на каждой станции по отдельности пики P/S-фаз сопоставляются между станциями для подтверждения сетевых событий — `core/associator.py`, построен на `run_associator_v2()` (`EQTransformer/utils/associator.py`):

- Группировка по **`p_arrival_time`** — физически точная опорная точка, а не начало 60-секундного окна (ошибка оригинального ассоциатора)
- **Скользящее окно** с шагом `moving_window/2` секунд гарантирует, что каждое событие полностью попадает хотя бы в одно окно
- Дедупликация перекрывающихся кандидатов
- Фильтр `_coherent_subset()`: итеративно исключает станцию с наибольшим числом нарушений неравенства треугольника (по временам P-прихода), не отбрасывая событие целиком

Перед самой ассоциацией `core/associator.py` дополнительно готовит стейджинг с фильтрацией по порогам вероятности/SNR и (опционально) учётом MC Dropout-неопределённости пиков — три режима (`UNCERTAINTY_MODE`): игнорировать неопределённость, взвешивать вероятности ею при передаче дальше, либо фильтровать по эффективной (уже взвешенной) вероятности. Подробности алгоритма и всех режимов — `core/associator.md`.

```bash
python core/associator.py --stations SOC,VSLR,BEYR --uncertainty-mode weight
```

**Секторный ассоциатор** (географическое разбиение сети на запад/восток) был опробован как способ снизить число ложных ассоциаций, но на практике проигрывал обычному сетевому ассоциатору по recall (терял события, чьи пики распределены между секторами) — перенесён в `legacy/`.

## Фильтрация по локальной магнитуде (ML)

Ассоциатор сам по себе не различает реальные события от шумовых микро-детекций иначе как по числу станций. Дополнительный этап — фильтрация по **локальной магнитуде** (формула Дягилева и др., 2023, калибровка для Терско-Каспийского прогиба):

- **`core/sta_correction_estimator.py`** — сопоставляет каталожные события с известной Ms с ассоциациями, измеряет амплитуду S-волны на каждой станции и вычисляет станционную поправку `S`, компенсирующую систематические отличия конкретной станции (грунт, азимутальная анизотропия, погрешности метаданных).
- **`core/ml_filter_v5.py`** — для каждого ассоциированного события снимает инструментальный отклик в окне вокруг S-пика, считает ML по каждой станции, агрегирует (медиана → σ-фильтр выбросов → среднее) и фильтрует `associations.xml` по порогу ML, применяя станционные поправки из предыдущего шага.

Подробности формулы, кэширования амплитуд и параллелизации — `core/sta_correction_estimator.md`, `core/ml_filter_v5.md`.

## Валидация и экспорт бюллетеня

Гипоцентр (координаты события) в пайплайне **нигде не вычисляется** — локации/триангуляции нет ни на одном этапе. Поэтому и валидация, и экспорт оценивают только время очага (T0), выводя его из разницы прихода P и S волн (S-P) на каждой станции, без привязки к координатам:

- **`core/validate_associator_v2.py`** — сравнивает ассоциации с эталонным каталогом (`catalog.xlsx`), считает recall. Реализовано пять способов агрегировать T0 по станциям события; эмпирически лучший — взвешивание по `p_probability × p_snr` (компенсирует систематическое запаздывание P-пика EQT, усиленное геометрией S-P формулы в ~2.4 раза). Старая версия (`validate_associator.py`, без этого анализа) — в `legacy/`.
- **`core/export_bul.py`** / **`core/compare_bul.py`** — экспорт всех прошедших фильтры ассоциаций в формат бюллетеня **IMS1.0:SHORT** (визуально похожий на официальные бюллетени ГС РАН) и сравнение с ними по времени и составу станций — независимая от `catalog.xlsx` (337 событий за весь 2024 год, малорепрезентативен) проверка качества пайплайна на большем массиве реальных событий.

Подробности — `core/validate_associator_v2.md`, `core/export_bul.md`, `core/compare_bul.md`.

## Возможные направления улучшения

### Локация события
- В пайплайне нет модуля локации/триангуляции по нескольким станциям — координаты события нигде не вычисляются. Это ограничивает точность оценки времени очага (S-P даёт лишь расстояние до станции, не направление) и делает часть событий принципиально невосстановимой при неудачной геометрии станций относительно радиационной диаграммы излучения (разобранный пример — `core/validate_associator_v2.md`).

### Ассоциатор
- **T0-фильтр согласованности на уровне ассоциации**: в дополнение к существующей проверке P-времён (`_coherent_subset`) — считать T0 из S-P для каждой станции ещё на этапе ассоциации и итеративно убирать станцию, наиболее удалённую от медианы T0, если разброс превышает порог. Идея зафиксирована, но не реализована — не решает случаи, где после отсева остаётся меньше `pair_n` станций.
- **Адаптивный `pair_n`**: для событий на границе сети требовать больше подтверждающих станций.

### Сеть станций
- Расширение с исходных 12 до ~60 станций уже выполнено; часть станций, добавленных позже, может случайно выпасть из отдельного прогона при неаккуратной передаче `--stations` — стоит сверять полноту списка станций перед каждым полным пересчётом.
- Метаданные сети (`Metadata/`) и архив волновых форм (`SDS/`) используют несовпадающие обозначения одной и той же сети (`N0` против `NO`) — не мешает при текущем составе обрабатываемых сетей, но встретится при попытке подключить эту сеть напрямую (см. `data_processors/README.md`).

### Модель и инференс
- **Дообучение на региональных данных**: EQT обучен на глобальных данных; дообучение на кавказских записях потенциально улучшит чувствительность к региональным механизмам очагов и скоростной модели коры.

## Установка

```bash
conda create -n eqt3 python=3.10
conda activate eqt3
conda install -c conda-forge cudatoolkit=11.2 cudnn=8.1.0
pip install tensorflow-gpu==2.10.0
pip install obspy "h5py==3.1.0" "numpy==1.19.2" scipy openpyxl
```

> **tensorflow-gpu** устанавливать через pip, не через conda (conda-версия давала hash mismatch).
> CUDA DLL должны быть в PATH — добавьте `$CONDA_PREFIX/Library/bin` через скрипт conda activate.d.
