# Прогон детектора на сервере (CPU) — `--gap-mode merge`

Инструкция для пересчёта детекций на сервере без интернета и ИИ-агентов: всё, что нужно,
— `git pull` и одна команда. Детектор — `core/cpu_pipeline.py` (CPU-обёртка над
`core/detector.py`), подробности — `core/cpu_pipeline.md`, `core/detector.md`.

**Зачем пересчитывать.** До фикса `--gap-mode merge` детектор обрабатывал суточный файл только
до первого разрыва записи (даже разрыва в несколько секунд) — остаток суток пропускался. На мае
2024 так терялось ~10% данных, на отдельных станциях до 50–70% (PXTR, URKR, UNCR, DBC, DRN).
`--gap-mode merge` склеивает куски записи и обрабатывает сутки целиком.

---

## 1. Обновить код и проверить, что фикс на месте

```
cd <путь к репозиторию>
git pull
conda activate eqt3
python core/cpu_pipeline.py --help
```

В выводе `--help` должна быть строка `--gap-mode {first-trace,merge}`. Если её нет — фикс не
приехал (не тот коммит/ветка), прогон не запускать.

## 2. Шаблон команды

```
python core/cpu_pipeline.py ^
    --gap-mode merge ^
    --estimate-uncertainty --number-of-sampling 5 ^
    --detection-threshold 0.75 --p-threshold 0.3 --s-threshold 0.2 ^
    --keep-ps --sp-limit 45 ^
    --max-workers 16 --tf-threads-per-worker 4 ^
    --input-dir   <каталог geofiles>  ^
    --json-dir    <каталог со station_*.json> ^
    --output-base-dir <каталог результата> ^
    --date-from 2025-01-01 --date-to 2025-04-01 ^
    --stations <СТАНЦИИ через запятую>
```

(`^` — перенос строки в Windows cmd; в Linux — `\`. Можно набрать одной строкой.)

**Обязательно указывать явно** (дефолты `cpu_pipeline.py` отличаются от майского GPU-прогона):

| Флаг | Значение | Почему |
|---|---|---|
| `--gap-mode merge` | merge | сам фикс; без флага — старое поведение (`first-trace`) |
| `--estimate-uncertainty` | вкл. | в `cpu_pipeline.py` MC Dropout по умолчанию **выключен**; все прогоны проекта — с ним |
| `--number-of-sampling 5` | 5 | по умолчанию 10; майский GPU-прогон и старый прогон 2025 — 5 |

Пороги (`0.75 / 0.3 / 0.2`, `--keep-ps`, `--sp-limit 45`) совпадают с дефолтами, в шаблоне они
для наглядности — менять не нужно.

**Даты.** `--date-from` включается, `--date-to` — нет. Фильтр работает по началу суточного файла
(файл 00:00–24:00), поэтому указывать целые сутки; время внутри суток не работает.

**Воркеры/потоки.** `--max-workers × --tf-threads-per-worker` ≈ число ядер (80 → например 16 × 4
или 20 × 4). Память: один воркер держит модель и сутки записи станции — 16–20 воркеров на 128 ГБ
должны помещаться; если сервер начнёт свопиться — уменьшить `--max-workers`.

**Время (оценка).** На домашнем ПК одни станцие-сутки с MC ×5 на 4 потоках CPU — ~1,8 мин.
При 20 воркерах это ~11 станцие-суток в минуту: 80 станций × 30 суток ≈ 2 400 станцие-суток
≈ 3,5–4 ч на месяц. Цифра грубая — уточнить по первому месяцу.

## 3. Что считать: 2025 Q1 и Q2, по кварталу за раз

Каждый квартал — отдельная команда и **отдельный `--output-base-dir`**: если прогон упадёт,
перезапускается только этот квартал (или только упавшие станции — см. раздел 4). Так же разбиты
и старые прогоны 2025 (`memory-25`: Q1 и Q2 отдельно) — сравнивать «было/стало» удобно.

| Квартал | `--date-from` | `--date-to` (не включается) | `--output-base-dir` (пример) |
|---|---|---|---|
| Q1 | `2025-01-01` | `2025-04-01` | `<...>/detector/output/2025_q1_merge` |
| Q2 | `2025-04-01` | `2025-07-01` | `<...>/detector/output/2025_q2_merge` |

Полная команда на квартал — шаблон из раздела 2 с этими датами. Вывод лучше сразу писать в файл,
чтобы потом проверить итог, например для Q1:

```
python core/cpu_pipeline.py --gap-mode merge --estimate-uncertainty --number-of-sampling 5 --max-workers 16 --tf-threads-per-worker 4 --input-dir <...> --json-dir <...> --stations <...> --date-from 2025-01-01 --date-to 2025-04-01 --output-base-dir <...>/2025_q1_merge > log_2025_q1.txt 2>&1
```

Если станции в Q1 и Q2 разные (как было в старых прогонах) — у каждого квартала свой `--stations`
(раздел 6). Время на квартал — оценка раздела 2 × 3 месяца (порядка полусуток при 80 станциях),
сервер можно оставить считать.

## 4. Проверка результата

- В конце вывода: `Успешно: N  Ошибок: 0`, где N — число станций в `--stations`.
- В `<output-base-dir>/<СТАНЦИЯ>/<станция>.csv` — файл у **каждой** станции (пустой CSV с одной
  строкой заголовка допустим, если у станции нет данных за период).
- Строки `[ERROR  ] <СТАНЦИЯ>` с traceback — эту станцию перезапустить отдельно (`--stations <СТАНЦИЯ>`,
  тот же `--output-base-dir`), остальные не трогать.
- `processing_log.csv` при параллельных воркерах перезаписывается (правило 12 `CLAUDE.md`) — по нему
  не проверять.

## 5. Что забрать домой

Каталоги `--output-base-dir` всех месяцев целиком (`<СТАНЦИЯ>/<станция>.csv`). Дальше дома —
`core/associator.py` → `core/ml_filter_v5.py` → `core/export_bul.py` → `core/compare_bul.py`.
Для `ml_filter_v5.py` (амплитуды) дома нужны и сами волновые файлы этих месяцев.
