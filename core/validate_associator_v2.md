# validate_associator_v2.py — описание алгоритма

## Цель

Сравнивает выход ассоциатора (`associations.xml`) с каталогом `catalog.xlsx`, считая recall (сколько каталожных событий нашлись среди ассоциаций) и расхождение по времени. Ключевая идея: **гипоцентр не вычисляется** — ни у ассоциатора, ни здесь нет локации (координат события), поэтому происхождение времени очага (origin time, T0) оценивается только из разницы прихода P и S волн на каждой станции (S-P), без привязки к координатам. Дополнительно (опционально) считает локальную магнитуду ML тем же способом, что `core/ml_filter_v5.py`/`core/sta_correction_estimator.py`, и может писать отфильтрованный по критериям результат обратно в QuakeML.

⚠️ **Эталон для оценки качества пайплайна — бюллетени ГС РАН (`workspace/bulletin/input/*.BUL`), проверка через `core/export_bul.py` → `core/compare_bul.py` (`--min-mag 1.5`), а не этот скрипт.** `catalog.xlsx` маленький (337 событий за весь 2024 год) и покрывает только западную часть региона. Recall этого скрипта — внутренняя диагностика, не итоговая метрика.

Origin time нужен, потому что сам ассоциатор (`run_associator_v2`) его не считает — только `min(p_arrival_time)` первой станции. Оценка из одних пиков (без координат) важна и на будущее: при реальном онлайн-мониторинге координаты события неизвестны до локализации, T0 в любом случае приходится оценивать так же.

## Оценка origin time из S-P (без координат)

Для каждой станции, где есть и P-, и S-пик:

```
ΔT  = Ts − Tp
R   = Vp·Vs / (Vp − Vs) · ΔT        (оценка гипоцентрального расстояния)
Tp0 = Tp − R / Vp                    (обратный расчёт времени очага от P)
Ts0 = Ts − R / Vs                    (то же от S — математически ≡ Tp0, тождество)
```

`T0` станции = `Tp0`. Так как `R` выводится из одной и той же пары `(Tp, Ts)`, `Tp0` и `Ts0` совпадают по построению — это не проверка согласованности, а тождество (второе значение считается для справки/отладки).

**Двухскоростная модель (`--dual-vel`, `estimate_origin_times_v2`):** на близких расстояниях P/S распространяются как коровые волны (`Pg`/`Sg`, `Vp`/`Vs` по умолчанию `6.0`/`3.4883` км/с), на дальних — как преломлённые на границе Мохо (`Pn`/`Sn`, быстрее: `VP_PN=8.0`, `VS_SN=4.6` км/с). Алгоритм: сначала считает `R` в коровой модели; если `R < R_PN_THR` (150 км) — использует `Pg/Sg` и на этом останавливается, иначе — пересчитывает `R` уже в модели `Pn/Sn` и использует её. Без `--dual-vel` используется только одна (коровая) модель на любом расстоянии — искажает `T0` для дальних станций, где реально уже работает `Pn/Sn`.

Станции с `R < --r-min` (по умолчанию 20 км, скользящая оценка — точки P и S ещё смешаны на близком расстоянии) или `R > --r-max` (если задан) исключаются из оценки `T0` события целиком.

## Отбраковка станций-выбросов: `sigma_filter`

Внутри одного события оценки `T0` по разным станциям расходятся (ошибки пиков, локальные искажения скорости). Фильтр:

```
med   = median(T0 по всем станциям)
σ     = population std(T0 − med)
inlier, если |T0 − med| <= --sigma · σ
```

Если после фильтрации остаётся меньше `MIN_STATIONS=3` станций — фильтр отменяется, используются все исходные станции без отброса (событие при этом получает флаг `[!N]` дальше по конвейеру — «мало станций для надёжной оценки»).

⚠️ **CLI-дефолт `--sigma 1.0`, но на практике используют `2.0`.** Эмпирическая проверка на майских 2024 данных (`σN>=6`, `Ms>=1.5`) показала, что более строгий порог режет слишком много станций и снижает recall:

| `--sigma` | Событий проходит `σN>=6` | Recall |
|---|---|---|
| **2.0** | 2184/3274 | **11/13** |
| 1.5 | 1646/3274 | 10/13 |
| 1.0 | 772/3274 | 10/13 |

При `--sigma 1.0` (значение по умолчанию) отбрасывается слишком много валидных станций как «выбросы» — событий с `σN>=6` заметно меньше, и часть реальных событий недобирает `--min-stations`. Смысл в контринтуитивно мягком пороге: σ здесь считается по всего нескольким станциям на событие, так что сама σ ещё нестабильна — жёсткий множитель усиливает эту нестабильность, а не компенсирует её.

## Пять способов оценить единый T0 события (`validate()`)

Из отфильтрованных (`inliers`) оценок `T0` по станциям строится одно число для события — сразу несколькими способами параллельно (все считаются всегда, какой из них использовать для матчинга с каталогом — решает `--match-by`):

| Оценка | Как считается | Смысл |
|---|---|---|
| `ot` (T0min) | `T0` станции с минимальным `ΔT(S-P)` | ближайшая станция — обычно наименее искажена распространением |
| `ot_raw` | среднее `T0` по **всем** станциям, без σ-фильтра | для сравнения — насколько фильтр вообще меняет картину |
| `ot_mean` | среднее `T0` по `inliers` (после σ-фильтра) | базовый метод, устойчив к единичным выбросам |
| `ot_wmean` | среднее, взвешенное по `1/ΔT²` | сильнее доверяет близким станциям (меньше ΔT — меньше геометрическое искажение) |
| `ot_probw` | среднее, взвешенное по `p_probability` из EQT | доверяет станциям с более уверенным P-пиком |
| `ot_probsnr` | среднее, взвешенное по `p_probability × p_snr` | учитывает и уверенность модели, и физическое отношение сигнал/шум одновременно — на практике даёт наименьшее расхождение с каталогом (см. журнал разработки) |

`ot_probw`/`ot_probsnr` требуют `--prob-dir` (папка `assoc_input` с `X_prediction_results.csv`, откуда берутся `p_probability`/`p_snr` по ключу станция+время P-пика) — без него остаются `None`, и `--match-by` с откатом (см. ниже) использует следующую доступную оценку.

`--match-by {min, mean, psnr}` выбирает, какая из оценок участвует в сравнении с каталогом (`min`→`ot`, `mean`→`ot_mean`, `psnr`→`ot_probsnr`); если выбранная оценка недоступна (`None`) для конкретного события — используется откат `ot_mean`, затем `ot`.

⚠️ **CLI-дефолт `--match-by min`, но на практике всегда используют `psnr`.** Причина — систематическая ошибка: EQT обучен находить пик по амплитуде волны, а не по моменту вступления, из-за чего P-пик модели немного запаздывает (`δTp`). Так как `T0 = Tp − R/Vp` и `R` растёт вместе с `ΔT(S-P)`, эта задержка усиливается коэффициентом `Vp/(Vp−Vs) ≈ 2.4` — запаздывание P-пика на 1–5с превращается в смещение T0 на 2–12с. Сравнение методов на 10 реальных событиях (май 2024, Ms≥1.5) дало:

| Метод | MAE | Макс. ошибка |
|---|---|---|
| `min` (ближайшая станция) | 14.8 с | — |
| `raw` (среднее без фильтра) | 6.1 с | — |
| `mean` (σ-фильтр + среднее) | 4.1 с | 13.2 с |
| `probw` (вес = `p_probability`) | 3.9 с | 12.8 с |
| **`psnr`** (вес = `p_probability × p_snr`) | **1.9 с** | **6.5 с** |

`min` (ближайшая станция) — самый ненадёжный: одна станция может дать единственный плохой пик, и оценку скорректировать нечем. `psnr` побеждает, потому что высокий SNR означает чёткий импульсный вход P-волны → пик модели точнее — вес одновременно учитывает и уверенность модели, и физическое качество записи. `ot_wmean` (вес `1/ΔT²`) на тех же данных получился **хуже** `mean`, а не лучше — близкая станция не обязательно даёт лучший пик EQT, поэтому агрессивное потенцирование веса по расстоянию не оправдано; метод оставлен в коде, но не рекомендуется.

**Двухскоростная модель (`--dual-vel`) даёт улучшение <1.5с** на тех же тестовых событиях — меньше, чем разброс от собственных ошибок пикинга EQT. Реализована и корректна, но включать её ради точности T0 отдельно от прочих факторов почти бессмысленно; заметный эффект она даёт только там, где станции реально далеко (`R > 150` км) и без неё T0 систематически искажён Pn-эффектом.

## Магнитуда ML (`compute_ml`)

Та же формула 5б (Дягилев и др. 2023), что в `ml_filter_v5.py`/`sta_correction_estimator.py`, реализована здесь заново, самостоятельно (не импортируется из тех файлов): `ML = lg(A_нм) + 1.024·lg(R) + 0.001648·R − 1.889 + S`, `R` — из той же S-P формулы (`_r_dict_all`, без нижнего/верхнего порога по расстоянию — фильтр применяется только внутри `compute_ml`). Отбор станций: `R >= ML_R_MIN(20)`, `A_NM_MIN(0.005) <= A_нм <= A_MAX_NM(1e6)`; агрегация — медиана → отброс станций с `|ML_i − median| > ML_SIGMA·σ` → среднее по оставшимся (если после отброса станций меньше `ML_N_MIN=4` — среднее по исходному набору).

⚠️ **`ML_SIGMA = 1`** здесь — заметно строже, чем `ML_OUTLIER_SIGMA = 1.5` в `ml_filter_v5.py`/`sta_correction_estimator.py` (там `2.0`). Три независимые реализации одной и той же идеи с тремя разными значениями порога — величины ML, посчитанные этим скриптом, не обязаны точно совпадать с `ml_filter_v5.py` на тех же данных.

ML требует `--amps` (CSV `pub_id,sta,A` — совместимый по формату с кэшем амплитуд `ml_filter_v5.py`/`sta_correction_estimator.py`) и опционально `--sta-corrections` (`station,S`, тот же формат, что у остальных ML-скриптов). `--no-amps` отключает расчёт ML полностью (например, когда важна только оценка T0/recall).

### `--distance-source {sp,locator}` — реальная дистанция вместо S-P-оценки (раздел 1.7d плана, 2026-09-13)

По умолчанию (`sp`) `R` в формулу ML по-прежнему берётся из `_r_dict_all()` (S-P-оценка, как описано выше) — поведение не меняется вообще. `--distance-source locator` вместо этого использует **реальную** дистанцию из `--hypocenters` (выход `core/locator.py`, LOCSAT) через `_r_dict_from_locator()`, но **только для событий с сошедшимся решением** (`converged=True`) — событие без решения (или отсутствующее в файле) автоматически откатывается на `_r_dict_all()` в этом же прогоне, не считается ошибкой (см. счётчик `R из локатора: N событий, fallback на S-P: M` в выводе).

Это не меняет главное свойство модуля — `write_quakeml` по-прежнему не пишет координаты события (см. ниже, "Известные особенности") — влияет только на то, каким `R` пользуется формула ML для конкретного события.

`--locator-distance-metric {hypocentral,epicentral}` (default `hypocentral`) — какую физическую величину считать за `R`:
- `hypocentral` (default): `R = sqrt(эпицентральная² + depth_km²)` — та же величина, что фактически даёт S-P-метод (S-P время зависит от полной длины луча, не только от горизонтальной дистанции), поэтому ML между `sp`/`locator` остаётся сравнимым, не меняя молча калибровку формулы Дягилева.
- `epicentral`: только горизонтальная (по поверхности) дистанция, без глубины.

Координаты станций для этого режима читаются отдельным лёгким загрузчиком `load_station_coords(--metadata-dir)` (ElementTree по StationXML) — независимая копия минимальной части `core/export_bul.py::load_station_coords()` (без fallback на `output_cpu_dir`, он там не нужен). `load_hypocenters(--hypocenters)` — независимая копия того же формата, что `core/export_bul.py`/`core/ml_filter_v5.py` (Rule 14: намеренное дублирование между независимыми потребителями, не унифицировано).

## Очищенный вход для LOCSAT: `--out-xml-inliers` / `--inliers-min-stations` (2026-10-07)

**Зачем.** Ассоциатор подмешивает в событие пики чужих, обычно далёких станций. Для оценки T0 это почти безвредно — σ-фильтр их отбрасывает. Но `core/locator.py`, получив сырой `associations.xml`, пытается объяснить **все** пики одной точкой и уходит на сотни км. Май 2024, сверка с бюллетенем ГС РАН (M ≥ 1.5): ошибка `R` по S-P на станциях, прошедших σ-фильтр, — медиана **10 км**, на отброшенных — **323 км**; эпицентр LOCSAT на сыром входе ошибается на сотни км, на очищенном — медиана **~4 км** там, где решение хорошее.

**Что делает.** `--out-xml-inliers PATH` (`write_quakeml_inliers()`) пишет QuakeML для `core/locator.py`:
- те же события с **тем же `publicID`** — `hypocenters.csv` стыкуется с `export_bul.py`/`ml_filter_v5.py`/этим скриптом без перевода ключей;
- пики **только станций, прошедших σ-фильтр T0** (`ae['inliers']`), — поэтому результат зависит от `--sigma` (проверено при `1.0`, дефолте);
- `Origin` **с координатами** ближайшей inlier-станции (min `ΔT(S-P)`) и временем `ot_mean` (откат на `ot`) — это только **стартовая точка** для LOCSAT, не гипоцентр. Обычный `--out-xml` координат не пишет, `locator.py` на нём не работает.

`--inliers-min-stations N` (default `4`): событие, у которого меньше `N` станций прошли σ-фильтр, в файл не пишется, то есть **не подаётся в LOCSAT**. Из пайплайна оно не удаляется: `export_bul.py` выводит его как раньше, без координат (fallback для событий без решения). Май 2024 после `ml_filter_v5` (548 событий): в файл попадает 319.

Обычный порядок (вход — выход `ml_filter_v5.py`):

```
python core/validate_associator_v2.py --assoc <associations_ml1p5.xml> --no-amps \
    --out-xml-inliers workspace/locator/input/<имя>_inliers.xml
# затем core/locator.py --assoc workspace/locator/input/<имя>_inliers.xml (seiscomp-python, см. locator.md)
# затем core/export_bul.py --locator-mode enrich ... → core/compare_bul.py --location-error ...
```

Скрипт при этом всё равно читает `--catalog` и печатает свой recall — побочный эффект общего `main()`, для этой задачи не нужен.

## Матчинг с каталогом

Для каждого каталожного события ищется ассоциация, чья оценка `T0` (по `--match-by`) ближе всего по времени и попадает в `±--window` секунд (по умолчанию 60с). Дополнительно можно потребовать минимум станций (`--min-stations`), считая либо по `N` — числу станций в XML вообще (`--min-stations-mode xml`), либо по `σN` — числу станций, прошедших σ-фильтр (`--min-stations-mode sigma`). Если у ближайшей по времени ассоциации станций недостаточно — событие не засчитывается как найденное, даже если оно ближе всего по времени (записывается в `missed`, но с указанием «ближайшего кандидата» для диагностики).

## Отчёты и режимы вывода

| Флаг | Что делает |
|---|---|
| (по умолчанию) | таблица найденных/пропущенных событий + recall + сводная таблица со столбцом `reason` (`окно` / `σN<X` / `окно+σN` — почему не засчитано) |
| `--show-picks` | для каждого найденного события — таблица пиков по станциям (`ΔT`, `R`, режим Pg/Pn, `p_prob`, ML станции, статус `OK`/`[!STA]` выброс) |
| `--show-all-picks` | то же самое, но для **всех** ассоциированных событий (не только совпавших с каталогом), с фильтром по `--year`/`--month` и `--min-stations` |
| `--show-flagged` | только события с флагом `[!N]` (меньше `MIN_STATIONS` станций прошли σ-фильтр) |
| `--show-all` / `--out-csv` | сводная таблица всех ассоциированных событий (T0, ML, MLH-если-совпало, R, N/σN) — в консоль или в CSV |
| `--out-xml` | пишет отфильтрованные (по `--year`/`--month`/`--min-stations`) ассоциированные события в новый QuakeML через `write_quakeml` |
| `--out-xml-inliers` | очищенный вход для `core/locator.py` (только σ-inlier пики + стартовые координаты) — см. раздел выше |

### `write_quakeml`

Пишет `Event`/`Origin`/`Magnitude`/`Pick*` в формате QuakeML BED 1.2. **Origin содержит только время** (`ot_probsnr`, с откатом на `ot`/`ot_mean`) — координаты не пишутся никогда, так как этот скрипт гипоцентр не вычисляет (см. также `core/export_bul.py`, который использует эту же логику для экспорта бюллетеня). Если посчитан ML — добавляется `Magnitude` типа `ML`. Вход для `core/locator.py` пишет отдельная `write_quakeml_inliers()` (`--out-xml-inliers`) — со стартовыми координатами.

## Диагностика: находки через `--show-picks`

### `coherence_tolerance` в ассоциаторе — расщепление bimodal-событий

При разборе конкретных событий через `--show-picks` обнаружилось, что старое значение `coherence_tolerance=15` (константа `core/associator.py`, проверка `_coherent_subset` в `EQTransformer/utils/associator.py`) пропускало пары станций, чьи P-пики принадлежали двум разным реальным событиям, разделённым на 25–35 с — они попадали в одну ассоциацию как «нормальный» разброс. Уменьшение до `coherence_tolerance=5` (покрывает ошибку EQT ~2с + погрешность скоростной модели ~2с, с запасом) расщепило такие bimodal-ассоциации на отдельные чистые события: **+1 recall (11/13 против 10/13)** и **+17% событий с ML≥1.5** на тех же майских данных — расщеплённое подсобытие получает корректный (не смешанный с чужими пиками) ML, и больше событий проходит порог. Сырое число ассоциаций при этом почти не меняется (62к против 65к) — эффект не в количестве, а в чистоте состава станций на событие.

**Ограничение**: не помогает, если P-приходы двух разных событий случайно совпадают по времени (см. ниже) — фильтр смотрит на согласованность времён, а не на физическую принадлежность события.

### Пример неустранимого промаха: событие 2024-05-06 12:25:10

Каталожное событие корректно детектировала только одна станция (SHA1, 296.8 км, T0 в пределах −0.9с от каталога). Ещё пять более близких станций (`NVPR`, `DVE`, `SRGR`, `DIGR`, `KMKR`) в то же примерное окно детектировали, судя по всему, **другое** событие — их T0 давали +25…+84 с относительно каталога. Вероятная причина — радиационная диаграмма излучения: SHA1 оказалась в направлении максимума излучения нужного события, а близкие станции — в узловой плоскости (низкая амплитуда) и вместо этого поймали более заметный сигнал соседнего события.

Почему это не лечится существующими фильтрами:
- **`coherence_tolerance=5` не спасает** — по случайному совпадению P-волна каталожного события до SHA1 (296 км) и P-волна постороннего события до ближней `SRGR` (22 км) разошлись по времени всего на ~4с, что прошло проверку согласованности случайно.
- **σ-фильтр T0 не спасает** — разброс шести станций дал `σ=26.6`с, порог `2σ=53.2`с пропускает даже станцию с отклонением +84с.
- **Итоговый `T0psnr=+19.9`с** — компромисс: SHA1 (самый высокий `p_prob=0.840`) тянет к правильному T0, пять «неправильных» станций тянут к постороннему событию.
- **Не лечится и параметрами ассоциатора** — единственная станция с правильным пиком (SHA1) физически меньше, чем любой разумный `pair_n>=2`, так что событие невозможно собрать только из корректных пиков.

Это иллюстрирует потолок точности всего подхода «T0 из одних только S-P пиков, без локации»: при определённом расположении станций относительно радиационной диаграммы события никакая перенастройка порогов не восстановит правильный результат — нужна была бы настоящая локация (инверсия по нескольким станциям), которой в пайплайне нет.

## Нереализованные идеи улучшения

- **T0 coherence filter на уровне ассоциатора** — в дополнение к существующему `_coherent_subset` (проверяет согласованность самих P-времён по формуле треугольника) предлагалось на уровне `core/associator.py`/`EQTransformer/utils/associator.py` дополнительно считать T0 из S-P для каждой станции ещё на этапе ассоциации и итеративно убирать станцию, наиболее далёкую от медианы T0, если разброс (`spread`) превышает порог. Для случая выше это разделило бы кластеры (`spread=85`с ≫ порога 15–20с), но одинокая SHA1 всё равно осталась бы ниже `pair_n` — событие было бы потеряно, а не исправлено; то есть даже этот фильтр не решает пример из предыдущего раздела до конца. **Не реализовано.**

## Известные особенности

- ML здесь и в `ml_filter_v5.py`/`sta_correction_estimator.py` — три отдельные, не связанные импортом реализации одной формулы с разными значениями порога `sigma` для отброса выбросов (`1.0` здесь, `1.5`/`2.0` там) — см. предупреждение выше.
- `--prob-dir` — обычно одна и та же папка `assoc_input`, даже если сравниваются XML из разных прогонов ассоциатора: `core/associator.py` перезаписывает `assoc_input` при каждом запуске, но если детектор не перезапускался между прогонами, содержимое (детекции по станциям) одно и то же независимо от того, какой конкретно `associations*.xml` сравнивается.
- `write_quakeml`/весь скрипт принципиально не пытаются вычислить координаты гипоцентра сами — этим с 2026-09-13 занимается отдельный `core/locator.py` (`context/locsat-plan.md`). `--distance-source locator` лишь **читает** его готовый результат для входа в формулу ML — не вычисляет координаты и не пишет их в QuakeML (`write_quakeml` по-прежнему пишет только время). Координаты в `write_quakeml_inliers()` — ближайшая станция как стартовая точка для LOCSAT, не гипоцентр.
- `--out-xml-inliers` использует тот же σ-фильтр, что оценка T0, поэтому зависит от `--sigma`. Проверено только при `--sigma 1.0` (дефолт); `2.0` (рекомендация выше для recall по `catalog.xlsx`) пропускает больше чужих станций — для входа LOCSAT это хуже, без отдельной проверки не использовать.
- Идея взвешивать T0 по `1/σ_p²` (MC Dropout неопределённость P-пика) на момент более раннего исследования не работала технически, так как `model.predict()` отключает dropout (std всегда ≈0). Это уже устранено на уровне детектора — `core/detector.py::worker_v4`/`predictor_mem_non_hdf_load_model_v6` реализует настоящий MC Dropout через `model(batch, training=True)` (см. `detector.md`) — но сам `validate_associator_v2.py` пока не считает T0-оценку, взвешенную по этой неопределённости (есть только `ot_probw`/`ot_probsnr`, использующие `p_probability`/`p_snr`, не `p_uncertainty`).
