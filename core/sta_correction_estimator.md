# sta_correction_estimator.py — вычисление станционных поправок ML

## Назначение

Вычисляет станционные поправки `S` для формулы ML (Дягилев et al. 2023, формула 5б)
на основе каталожных событий с известной магнитудой Ms.

Поправка компенсирует систематические отличия конкретной станции от модели:
особенности грунта, азимутальная анизотропия, погрешности в StationXML.

Выход (`--out-summary`) — это тот самый CSV, который `core/ml_filter_v5.py` принимает через `--sta-corrections`.

---

## Как это работает

### Шаг 1 — Матчинг каталога с ассоциатором

Для каждого события из `catalog.xlsx` ищется ближайшее по времени событие
в `associations.xml`, с поправкой на время пробега P-волны до ближайшей станции:

```
expected_assoc_time = catalog_origin_time + P_travel_time_to_nearest_station
совпадение если |assoc_time − expected| ≤ match_win (по умолчанию 15 с)
```

Алгоритм совпадает с `validate_associator.py`. При нескольких XML-событиях в окне выбирается ближайшее по времени (`match_catalog_to_xml`); если ни одно не попало в окно — каталожное событие просто не участвует дальше.

### Шаг 2 — Расстояние R до каждой станции

Два режима (`--use-coords`):

| Режим | Формула | Требует |
|---|---|---|
| **по умолчанию** — S-P ΔT | `R = Vp·Vs/(Vp−Vs) · ΔT(S-P)` | и P-, и S-пик станции в XML |
| **`--use-coords`** | `R = sqrt(epi² + depth²)`, `epi` — haversine от каталожного (lat, lon) до координат станции (`json/station_*.json`) | только S-пик (для окна амплитуды); координаты и глубина берутся из каталога, а не из S-P |

`--use-coords` точнее там, где известна локация каталожного события (эпицентр каталога обычно надёжнее, чем S-P на шумной записи), но зависит от точности каталожных координат/глубины. Оба режима фильтруют по `--r-min` (по умолчанию `R_MIN_KM=30` — при более близких расстояниях P-кода накладывается на S-волну и завышает амплитуду) и `--r-max` (`R_MAX_KM=600`, `0` = без ограничения).

### Шаг 3 — Измерение амплитуды S-волны

Для каждого совпавшего события на каждой станции:
- Берётся горизонтальная компонента, приоритет **E > N > Z** — выбирается **один раз на станцию**, по всем доступным файлам (`build_waveform_index`), а не отдельно на событие.
- События группируются по файлу и кластеризуются по времени (`MAX_GROUP_SPAN_SEC=300`с), чтобы читать один файл одним вызовом `obspy_read`, с запасом `READ_MARGIN_SEC=120`с по краям для `remove_response`.
- После чтения вызывается `st.merge(method=0, fill_value=0)` — пропуски внутри окна заполняются нулями, чтобы трасса гарантированно покрывала весь запрошенный диапазон (в `ml_filter_v5.py` этого шага нет — минимальное, но реальное расхождение между «близнецами»).
- Снимается инструментальный ответ: `remove_response(output='DISP', pre_filt=(0.5, 1.0, nyq·0.85, nyq·0.95), water_level=60)` → смещение грунта в метрах; по умолчанию затем полосовой фильтр 1–5 Гц (`--no-bandpass` отключает).
- Окно `[S_time .. S_time + win_sec]` (`--win-sec`, по умолчанию 5с) вырезается из трассы; результат принимается только если в срезе набралось не меньше `max(1, sr·win_sec·0.5)` отсчётов (защита от обрезанных на границе файла окон) — в `ml_filter_v5.py` проверяется только на `len(...) == 0`, порог здесь строже.
- Максимум `|данных|` в окне = амплитуда A (м).

Обработка параллельная: станции (не события) делятся round-robin по `--workers` потокам, каждый воркер работает только со своими файлами.

### Шаг 4 — Вычисление поправки на пару (событие, станция)

Для каждой пары, независимо (не через агрегацию по станциям события, как в `ml_filter_v5.py` — здесь единица анализа — одна станция на одно каталожное событие):

```
ML_raw  = lg(A_нм) + 1.024·lg(R) + 0.001648·R − 1.889
S_ev    = Ms_каталог − ML_raw
```

`ML_raw` — магнитуда без поправки (`compute_raw_ml`, фильтрует только `A_nm <= 0` и `A_nm > A_MAX_NM=1e6` — нижнего порога амплитуды здесь нет, в отличие от диагностического пути ниже). `S_ev` — поправка, необходимая чтобы формула дала каталожную магнитуду.

Перед сохранением строка может быть отброшена двумя независимыми фильтрами (`compute_corrections`, оба выключены по умолчанию, `0` = выкл.):
- **абсолютный** по `lg(A_нм)` — `--lg-a-min`/`--lg-a-max`: отсекает шум снизу / насыщение сверху;
- **относительный** (`amp ratio`) — `--amp-ratio-max` (по умолчанию `5.0`) / `--amp-ratio-min` (по умолчанию `0.0`, выкл.): сравнивает измеренную амплитуду с ожидаемой по каталожной `Ms` и `R` (`10^(Ms − b_log·lg(R) − b_lin·R − c)`), отбрасывает измерения дальше чем `ratio×` от ожидания в любую сторону.

### Шаг 5 — Усреднение и детектор выбросов по станции

По каждой станции собирается вектор `[S_ev_1, S_ev_2, ..., S_ev_N]` (`aggregate_by_station`).

Выбросы определяются методом IQR (только если у станции ≥ 4 событий, иначе все считаются inlier):
```
Q1, Q3 = 25-й и 75-й перцентили
IQR    = Q3 − Q1
выброс если S < Q1 − iqr_k·IQR  или  S > Q3 + iqr_k·IQR   (iqr_k = --iqr-k, по умолч. 1.5)
```

Итоговая поправка = **среднее без выбросов** (`mean_clean`). В терминал выводится и `mean_all` (с выбросами) для сравнения, но **в файл всегда пишется `mean_clean`** — CLI-флага, чтобы записать `mean_all`, нет (`save_summary_csv` вызывается с `use_clean=True` жёстко в `main()`).

Станция включается в результат только если `N >= --min-events` (по умолчанию 6).

## Режим `--info` — только матчинг

Не извлекает амплитуды и не строит кэш — только прогон шагов 1–2 (матчинг + расчёт R) и таблица:

```
Время каталога          Ms   dt,с  N_sta  pub_id
2024-01-05 14:23:11.00  1.2    3.4      5  smi:local/...
```

Полезно, чтобы быстро проверить, сколько каталожных событий вообще находят пару в XML и со сколькими станциями, прежде чем запускать дорогое извлечение амплитуд.

## Режим `--diag-ml` — ML станции vs Ms каталога

Требует уже готового кэша амплитуд (`--cache-amp`, без `--rebuild-cache` не строится заново) и файла поправок (`--sta-corrections`, по умолчанию — тот же `--out-summary`, то есть свой собственный последний выход). Для каждого совпавшего события агрегирует ML по станциям **одним из двух методов** и печатает расхождение с каталожной Ms:

```
Время каталога          Ms    ML      Δ   N  Станции использованы  [отброшены выброс]
2024-01-05 14:23:11.00  1.2  1.34  +0.14   5  BEYR DOMR GOYR SHA1 SOC  [NEUR]

Δ = ML − Ms  →  mean=+0.05  median=+0.03  std=0.18  N=42
```

Два метода агрегации (флаг `use_v2` внутри кода, не вынесен в CLI — используется `compute_event_ml_detail_v2`, то есть v2, по умолчанию):

| Метод | Функция | Алгоритм |
|---|---|---|
| **v2 (по умолчанию)** | `compute_event_ml_detail_v2` | медиана → отбросить `\|ML_i − M_med\| > ML_OUTLIER_SIGMA·σ` (2.0) → среднее по оставшимся |
| v1 (legacy) | `compute_event_ml_detail` | итеративный ratio-фильтр (`_ML_RATIO_MIN=0.1`) → медиана |

`--exclude-stations` действует **только в `--diag-ml`** — на основной расчёт поправок (шаги 3–5 выше) не влияет; это явно указано в help-строке флага в коде.

⚠️ Расхождение с `ml_filter_v5.py`: комментарий в коде говорит, что константы диагностики «должны совпадать с `core/ml_filter_v5.py`», но по факту не совпадают (значения в `v5` не менялись при переходе с `v4` — расхождение старое, не новое):

| Константа | здесь | в `ml_filter_v5.py` |
|---|---|---|
| `R_MIN_KM` | 30 | 20 |
| `A_NM_MIN` | 0.01 (не используется в основном расчёте поправок, только в `--diag-ml` v2) | 0.005 |
| `_ML_N_MIN_STA` / `N_MIN_STA` | 3 | 4 |
| `ML_OUTLIER_SIGMA` | 2.0 | 1.5 |
| `READ_MARGIN_SEC` | 120 | 60 |

Соответственно, число ML, посчитанное `--diag-ml`, не обязано точно совпадать с тем, что даст `ml_filter_v5.py` на тех же данных — это независимая (хоть и похожая) реализация для самопроверки, а не вызов той же функции.

**Убрано (2026-09-06, `production-plan.md` Трек 1).** Константа `ML_OUTLIER_ABS = 0.3` была упомянута в докстринге `compute_event_ml_detail_v2` («удалить выбросы: `|MLi − Mmed| > outlier_abs` ИЛИ `> outlier_sigma·σ`»), но фактически в теле функции не использовалась — фильтрация всегда шла только по `outlier_sigma·σ`. Константа удалена, докстринг приведён в соответствие с кодом (только σ-условие); предыдущая версия — `legacy/sta_correction_estimator.py`.

## Запуск

```powershell
conda activate eqt3

# Посмотреть только матчинг (без чтения форм волн)
python core/sta_correction_estimator.py --info --year 2024 --month 1

# Вычислить поправки (январь 2024, мин. 10 событий на станцию)
python core/sta_correction_estimator.py --year 2024 --month 1

# Мягче: мин. 5 событий на станцию
python core/sta_correction_estimator.py --year 2024 --month 1 --min-events 5

# Только по сильным событиям (Ms >= 1.0)
python core/sta_correction_estimator.py --year 2024 --month 1 --min-ms 1.0

# R из координат каталога вместо S-P (нужен только S-пик)
python core/sta_correction_estimator.py --year 2024 --month 1 --use-coords

# Пересобрать кэш амплитуд
python core/sta_correction_estimator.py --rebuild-cache --year 2024 --month 1

# Кастомные пути (например, другой прогон ассоциатора)
python core/sta_correction_estimator.py `
  --assoc-in workspace/associator/output/associations_weight_v2.xml `
  --out-summary workspace/magnitude/output/sta_corrections_new.csv `
  --year 2024 --month 1

# Ослабить IQR-фильтр (больше выбросов оставить)
python core/sta_correction_estimator.py --year 2024 --month 1 --iqr-k 2.0

# Больше воркеров
python core/sta_correction_estimator.py --year 2024 --month 1 --workers 8

# Диагностика: ML (v2, медиана→2σ→среднее) vs Ms по каждому событию,
# с уже посчитанными поправками и кэшем
python core/sta_correction_estimator.py --diag-ml --year 2024 --month 1
```

## Важные замечания

- `_PAZ_WA` (полюса/нули/чувствительность Wood-Anderson) — определялся в коде, но нигде не использовался (WA-симуляция не применяется в этом скрипте, как и в `ml_filter_v5.py`: формула 5б ожидает смещение грунта, не WA-амплитуду); удалён 2026-09-06 (`production-plan.md` Трек 1), в `legacy/sta_correction_estimator.py` ещё присутствует.
- Кэш `--cache-amp` (по умолчанию `workspace/magnitude/output/amps_corrections_cache.csv`) отдельный от кэша `ml_filter_v5.py` (`workspace/magnitude/output/amps_filter_cache.csv`). Это разные наборы событий: здесь только каталожные события с известной Ms, там — все события ассоциатора.
- При смене `--assoc-in`, `--year/--month` или `--use-coords` нужен `--rebuild-cache` (набор пар `(pub_id, sta)` меняется). При смене `--amp-ratio-max/min`, `--lg-a-min/max` или `--win-sec` — **не нужен** (кэш хранит сырые амплитуды в метрах, все фильтры применяются позже, на этапе `compute_corrections`).
- **Amplitude ratio filter** (`--amp-ratio-max 5.0`): удаляет измерения где `A_nm > 5×` ожидаемой амплитуды по каталожной Ms и R. Ловит шум и сбои `remove_response`, но **не** затрагивает станции с аномально низкой амплитудой (`--amp-ratio-min` выключен по умолчанию — если понадобится симметричный фильтр, включать его нужно отдельно).
- Основной расчёт поправок (`compute_raw_ml`/`compute_corrections`) **не фильтрует по нижнему порогу амплитуды** (`A_NM_MIN` там не применяется) — только по `A_nm > A_MAX_NM`. Нижний порог используется исключительно в `--diag-ml` (v2-путь).
- Выбросы чаще всего означают: плохой пик S у конкретного события на станции, или сбой `remove_response` (шум в окне S-волны).
- Значения по умолчанию (`gpu_splimit_45_may`, файлы `*_may_*`) относятся к конкретному майскому прогону 2024 года — при работе с другим прогоном (`gpu_splimit_45_march`, `..._may_v2` и его `assoc_output_lim_{filter,none,weight,weight_v2}`) все связанные пути (`--assoc-in`, `--cache-amp`, `--out-summary`) нужно указывать явно, дефолты под них не заточены.
