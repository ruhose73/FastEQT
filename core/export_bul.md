# export_bul.py — описание алгоритма

## Цель

Экспортирует все ассоциированные события в бюллетень формата **IMS1.0:SHORT** — тот же визуальный формат, в котором ГС РАН публикует официальные бюллетени (`bul/*.BUL`), чтобы результат можно было сравнить с ними (`core/compare_bul.py`) или передать в НИИ. В отличие от `validate_associator_v2.py`, здесь **нет сравнения с `catalog.xlsx`** — на выходе все события, прошедшие фильтры, без привязки к тому, есть ли для них каталожный аналог.

Гипоцентр (координаты/глубина) по умолчанию (`--locator-mode off`) **не вычисляется** — поля `Lat/Lon/Depth` и всё, что от них производно (`Smaj/Smin/Az/RMS`), в бюллетене остаются пустыми, `location method='o'` (S-P, без инверсии). `mdist`/`Mdist` (мин/макс эпицентральное расстояние в градусах) — не исключение: они получены из `R_km` (S-P расстояние до станции), переведённого в градусы (`KM_PER_DEG=111.195`), а не из настоящего эпицентра — это можно посчитать и без координат события, поэтому заполняются всегда, независимо от режима локатора.

С `--locator-mode enrich` или `filter` (`context/locsat-plan.md`, Шаг 5, реализовано 2026-09-13) в бюллетень подключается выход `core/locator.py` (LOCSAT через SeisComP, `--hypocenters`, по умолчанию `workspace/locator/output/hypocenters.csv`) — см. раздел "Интеграция локатора" ниже.

## Переиспользование `validate_associator_v2.py`

Скрипт **не переопределяет** логику оценки времени очага и магнитуды заново — импортирует `core/validate_associator_v2.py` как модуль (`sys.path.insert` + `import validate_associator_v2 as v2`) и напрямую использует оттуда: `estimate_origin_times_v2` (двухскоростная модель Pg/Sg-Pn/Sn), `sigma_filter` (отброс станций-выбросов), `compute_ml` (магнитуда по формуле 5б), `load_associations`/`load_amplitudes`/`load_pick_probabilities`, а также константы по умолчанию (`v2.DEFAULT_ASSOC`, `v2.DEFAULT_AMPS`, `v2.DEFAULT_VP/VS/SIGMA`, `v2.MIN_STATIONS`). Дублирования формулы здесь нет (в отличие от того, что `ml_filter_v5.py`/`sta_correction_estimator.py`/`validate_associator_v2.py` реализуют её формулу независимо друг от друга — см. предупреждение в `validate_associator_v2.md`).

Всегда используется **двухскоростная** модель (`estimate_origin_times_v2`) — без разделения на `Pg/Sg`/`Pn/Sn` сам код фаз (`Phase` в бюллетене — `Pg`/`Pn`/`Sg`/`Sn`) не имел бы смысла; в отличие от `validate_associator_v2.py`, здесь это не опция (`--dual-vel`), а всегда включённое поведение.

## Отсев не-кавказских станций (`filter_far_stations`)

Во входных данных `--prob-dir` (`workspace/associator/input`, см. `DEFAULT_PROB_DIR`) вперемешку с региональной кавказской сетью (станции максимум ~700 км друг от друга, Сочи–Дербент) попали опорные/референсные станции по всей России — вплоть до Владивостока и Антарктиды, на 1300+ км дальше самой дальней настоящей кавказской станции. Это не намеренный выбор станций для этого экспорта, а особенность состава входных данных.

`filter_far_stations` убирает из пикинга события станции дальше `--max-station-dist-km` (по умолчанию 800 км) от опорной точки (`--ref-lat`/`--ref-lon`, по умолчанию — Сочи 43.6/40.0, константы `CAUCASUS_REF_LAT/LON`; флаги добавлены 2026-10-07, раньше точка была только константой), **до** расчёта T0/ML — считается расстояние по координатам станции (haversine), не по названию/региону, иначе легитимные, но не описанные в `--metadata-dir` станции (например `KGUR`/`MRMR`) отсеклись бы наравне с настоящими дальними. Станции, для которых координаты вообще не найдены (`load_station_coords` не дал результата), **не отбрасываются вслепую** — остаются в расчёте, чтобы не терять данные там, где просто не хватает метаданных.

`load_station_coords` берёт координаты в первую очередь из `--metadata-dir/*.xml` (StationXML), а для станций, которых там нет — как fallback, из первой строки их CSV в `--output-cpu-dir` (`station_lat`/`station_lon`, колонки, которые пишет сам детектор).

`--max-station-dist-km 0` (или отрицательное значение) отключает фильтр целиком.

## Определение региона в шапке события (`load_station_regions`)

Поле региона в строке `EVENT` определяется по административному региону **ближайшей станции** события, а не по вычисленному эпицентру (которого нет). Регион берётся из `--metadata-dir/{NET}_{STA}_*.xml` — поле `Site/Name` в StationXML, часть строки после первой запятой (обычно город, регион, страна — берётся именно регион). `REGION_ALIASES` нормализует типовые варианты написания (`"dagestan rep."` → `"DAGESTAN REGION"` и т.п.) к формату, похожему на официальные бюллетени. `STATION_REGION_OVERRIDES` — точечное исправление опечатки в одном конкретном файле метаданных (`TMNR`: точка вместо запятой после города в `Site/Name`, из-за которой парсер иначе брал бы `"Russia"` как регион). Если региона для станции не нашлось — используется `DEFAULT_REGION` ("NORTH CAUCASUS REGION").

## Обработка события (`process_events`)

По структуре — то же самое, что делает `validate_associator_v2.validate()` внутри цикла по ассоциациям, но без сопоставления с каталогом:

1. `filter_far_stations` — убрать дальние станции (см. выше).
2. `estimate_origin_times_v2` — оценка T0 по каждой станции (двухскоростная модель).
3. `sigma_filter` — отброс станций-выбросов; если после этого меньше `v2.MIN_STATIONS` — `n_flag=True`.
4. Итоговый T0 события = `ot_probsnr` (взвешенное по `p_probability × p_snr`, требует `--prob-dir`), с откатом на `ot` (T0 ближайшей по `ΔT(S-P)` станции), если `ot_probsnr` недоступен. Других вариантов T0 (`mean`/`wmean`/`probw`, которые есть в `validate_associator_v2.py`) здесь не считается — выбор фиксирован.
5. Если ML нужен (`amplitudes` загружены) — `compute_ml` по всем станциям с P+S пиком (`v2._r_dict_all`, без нижнего/верхнего порога по `R` — фильтр по расстоянию применяется только внутри `compute_ml`).
6. `n_def` — число «определяющих» фаз (P или S) по всем станциям после отсева дальних, до σ-фильтра — используется как `Ndef` в бюллетене.

## Формат IMS1.0:SHORT

### Байтовая раскладка колонок

Комментарий в коде фиксирует источник раскладки: официальная спецификация **IDC-3.4.1Rev1** («Formats and Protocols for Messages — IMS1.0», IDC/ISC), таблицы 41 (Origin Block) и 42 (Phase Block). Колонки Phase Block сверены побайтово с примерами из приложения A документа и совпадают точно; колонки Origin Block сверены по номерам колонок из той же таблицы (пример в PDF, из которого извлекался текст, терял часть пробелов при экстракции, поэтому использованы только числовые границы колонок из спецификации, не сам образец).

⚠️ **Раскладка — приближение к визуальному виду `bul/*.BUL`, не побайтовая копия официального формата целиком.** Только реально заполняемые поля (`Date`, `Time`, `Ndef`, `Nsta`, `Author`, `OrigID`, `Sta`, `Phase`, `Time`, `SNR`, `Amp`, `Magnitude`, `ArrID` — всегда; `Latitude`/`Longitude`/`Depth`/`Err depth`/`RMS` — только с `--locator-mode enrich|filter`, см. "Интеграция локатора" ниже) выровнены по спецификации/образцу вручную; остальные позиции — просто зарезервированное пробелами место. Перед отправкой во внешнюю организацию рекомендуется сверить пару событий глазами с образцом.

**`Def`** (колонки 74–76 Phase Block) — не одна строка `"T__"` куском, а три независимых однобайтовых флага: time/azimuth/slowness defining. `"T__"` получается именно потому, что у нас определено только время прихода, но не азимут и не медленность — это зафиксировано отдельным комментарием в коде, так как раньше было источником бага (`Def` «наезжал» на соседнее поле `SRes` при неверной трактовке ширины).

### `_put(chars, start, end, value, align)`

Общий помощник форматирования: вставляет `value` в список символов фиксированной длины на позиции `[start, end]` (1-индексация, включительно, как в спецификации), обрезая/дополняя пробелами по `width = end - start + 1`. `fmt_origin_line`/`fmt_magnitude_line`/`fmt_pick_line` — обёртки над ним для каждого из трёх типов строк (`ORIGIN_LEN=136`, `MAG_LEN=38`, `PHASE_LEN=122` символов).

### Захардкоженные поля

`AUTHOR = "EQT"`; `analysis type = 'a'` (automatic); `location method = 'o'` (other — оценка по S-P, без инверсии) либо `'i'` (inversion — событие получило решение `core/locator.py`, только при `--locator-mode enrich|filter`, см. выше); `event type = 'uk'` (unknown — не верифицировано вручную); `pick type = 'a'` (automatic); short-period motion и onset quality — всегда `'_'` (null, не определяются моделью).

### Структура выходного файла (`write_bul`)

```
DATA_TYPE BULLETIN IMS1.0:SHORT
NORTH CAUCASUS REGION Bulletin (EQTransformer, automatic, for review)

EVENT <orig_id> <регион>
<ORIGIN_HEADER>
<строка гипоцентра (без Lat/Lon/Depth)>

<MAG_HEADER>              (только если ML посчитан)
<строка магнитуды>

<PICK_HEADER>
<строка P или Sg/Sn на станцию, в порядке времени пика>
...

... (повтор EVENT-блока на каждое событие, отсортированы по T0)
STOP
```

`Phase` пика — `Pg`/`Sg` или `Pn`/`Sn` в зависимости от того, в каком скоростном режиме была оценена станция (`estimate_origin_times_v2` возвращает `regime` на станцию); режим S-фазы наследуется от режима P той же станции (`Sg` при `Pg`, `Sn` при `Pn`).

## Интеграция локатора (`--locator-mode`, Шаг 5 плана, 2026-09-13)

Архитектура — раздел 1.7b `context/locsat-plan.md`, согласована с пользователем: `core/locator.py`
считает только сырые метрики (не трогается этим шагом, Rule 13), решение "проходит/не проходит"
принимает исключительно `export_bul.py` — по аналогии с парой `detector.py`(метрика)/`associator.py`
(порог, `_passes_v2()`).

- **`--locator-mode off`** (default) — точное старое поведение, `--hypocenters` не читается вообще.
- **`--locator-mode enrich`** — `load_hypocenters(--hypocenters)` строит `event_id -> строка CSV`
  (ключ — тот же `publicID`, что `ae['pub_id']`). Для события с сошедшимся решением
  (`converged=True`) `fmt_origin_line_v2()` вызывается вместо `fmt_origin_line()`: заполняет
  Latitude/Longitude/Depth/Err(depth)/RMS и меняет `location method` с `'o'` на `'i'` (inversion,
  по спецификации IMS1.0). Событие без решения (`converged=False`, либо `event_id` не найден в
  CSV вовсе — например, файл не пересобирался после последнего прогона ассоциатора) получает
  старое поведение, без исключений/ошибок.
- **`--locator-mode filter`** — то же, что `enrich`, плюс отбрасывает те события, у которых решение
  ЕСТЬ, но не проходит `_passes_locator_quality()`. Событие БЕЗ решения локатора **не** считается
  провалившим фильтр — оно остаётся в выдаче со старым поведением, ровно как в `enrich`. Именно это
  различие ("нет решения" ≠ "плохое решение") — прямая реализация явного требования плана (раздел 7).

`_passes_locator_quality(row, max_rms, min_depth_uncertainty_km)`:
- `depth_uncertainty_km` ниже `--locator-min-depth-uncertainty-km` (по умолчанию `0.001`, то есть
  практически "== 0") — отбрасывается. Это не догадка: `context/locsat-plan.md` раздел 5 показал на
  20 событиях сэмпла, что `depth.uncertainty() == 0.0000` надёжно отличает упор решения в границу
  таблицы годографов (0 или ~750 км) от настоящей решённой глубины (там же ненулевая погрешность,
  напр. `131.6 ± 6.04`) — не отдельная физически осмысленная категория событий.
- `rms` выше `--locator-max-rms` — отбрасывается, **только если флаг задан явно**. По умолчанию
  `None` (не проверяется) — откалиброванного порога по умолчанию нет; сознательно не выдумывается.
  На мае 2024 у решений с ошибкой эпицентра до 10 км RMS < 1 с, у плохих ≥ 5.6 с, но `filter`
  с порогом 2 с всё равно теряет реальные события (см. проверку ниже).

Оба CLI-флага порогов не имеют смысла с `--locator-mode off`/`enrich` (в `enrich` `filter`-логика
просто не вызывается).

### Проверка на мае 2024 против бюллетеня ГС РАН (2026-10-07)

`compare_bul.py --min-mag 1.5 --window 60`, наш вход — `associations_ml1p5.xml` (548 событий),
`--hypocenters` — LOCSAT на очищенном входе (`validate_associator_v2.py --out-xml-inliers`, ≥ 4
станций; 157 из 319 сошлось):

| `--locator-mode` | Событий | С координатами | Recall, min-shared=1 | min-shared=4 |
|---|---|---|---|---|
| `off` | 548 | 0 | 37/46 | 36/46 |
| `enrich` | 548 | 157 | **37/46** | **36/46** |
| `filter` (`--locator-max-rms 2.0`) | 435 | 44 | 31/46 | 30/46 |

- **`enrich` событий не теряет** — тот же recall, что `off`, плюс координаты. Рабочий режим.
- **`filter` теряет реальные события** (−6 из 37 при M ≥ 1.5) — в текущем виде не использовать.
- `enrich` пишет координаты **любого** сошедшегося решения, в том числе упёршегося в границу
  таблицы годографов (глубина 0 или 750 км): `compare_bul.py --location-error` показал у таких
  событий ошибку эпицентра 100–660 км, у остальных — медиана единицы км.
- На сыром `associations.xml` (без очистки пиков) LOCSAT ошибается на сотни км почти везде — подавать
  в `core/locator.py` выход `--out-xml-inliers`, см. `validate_associator_v2.md`.

### Позиции колонок Latitude/Longitude/Depth/Err(depth)/RMS

Эти поля не были в `ORIGIN_HEADER`-раскладке до Шага 5. Их позиции **не** взяты из PDF-спецификации
IDC-3.4.1Rev1 на глаз: при извлечении текста из двухколоночной вёрстки этого конкретного PDF
(`pdftotext -layout`) Position/Format-числа для строк "2-n (data)" перемешиваются с описаниями полей
не в том порядке (проверено на практике 2026-09-13 — числа сами по себе не ошибочны, но без надёжной
привязки к названию поля их нельзя использовать вслепую). Вместо этого позиции выверены побайтово по
двум независимым реальным источникам, давшим идентичный результат: официальный бюллетень ГС РАН
(`workspace/bulletin/input/2024_jan-dec_NCAU.BUL`) и пример вывода `out_format=IMS1.0` с сайта ISC
(событие 11691339). Итоговые границы (1-индексация, включительно): `RMS` 31–35, `Latitude` 37–44,
`Longitude` 46–54, `Depth` 72–76 (плюс флаг фиксации глубины в колонке 77), `Err depth` 78–82 —
`fmt_origin_line_v2()` использует их через тот же `_put()`.

Числа этих полей форматируются `_fmt_fit()` — переменной точностью (2→0 знаков после запятой для
RMS/Depth/Err depth), а не жёстко `.2f`/`.1f`: `_put()` при переполнении молча обрезает строку СЛЕВА,
что для числа испортило бы значение (пример из реальных данных сэмпла — RMS `119.41` при жёстком
`.2f` не влезает в 5-символьное поле и превратилось бы в `19.41`). Latitude/Longitude — всегда `.4f`
без адаптации: географические границы (±90/±180) гарантированно помещаются в 8/9 символов.

### Dist / EvAz в строках фаз (2026-10-09)

При `--locator-mode enrich|filter` у событий с решением локатора (`converged=True`) в каждой строке фазы
заполняются **Dist** (эпицентральное расстояние, градусы дуги, колонки 7–12) и **EvAz** (азимут очаг →
станция, градусы от севера по часовой, 0–360, колонки 14–18), как в бюллетене ГС РАН. Считает
`_dist_az_deg()` (сфера) по координатам LOCSAT и станции (`load_station_coords()`: StationXML, откат —
первая строка CSV детектора). Строку пишет `fmt_pick_line_v2()` — рядом со старой `fmt_pick_line()`
(правило 13); без Dist/EvAz её выход побайтово тот же. Dist < 1° — без ведущего нуля (`.86`), как у
ГС РАН. При `--locator-mode off` выход побайтово прежний (проверено на мае 2024, merge_p6), у события
без решения локатора поля пустые. Плохие решения (упор глубины в границу, большой RMS) тоже получают
Dist/EvAz — по решению пользователя плохие координаты в бюллетене оставляются.

Проверка формулы по первому событию бюллетеня ГС РАН 2024 (эпицентр 40.705 / 47.230, 13 станций):
Dist совпадает до 0.01°, EvAz — в пределах 1.1° (AKT 26.1 у ГС РАН против 25.1 у нас, LACR 314.0
против 315.1, остальные ≤ 0.5°). Геоцентрическая поправка широты на результат почти не влияет;
остаток — вероятно, различия координат станций/точности эпицентра. `compare_bul` читает из строк
фаз только код станции (колонки 1–5) — recall не меняется (май 2024, merge_p6: 40/46 и в `off`, и в
`enrich`).

## Известные особенности

- Формат — визуальное приближение, не побайтовая копия официальной спецификации целиком (см. выше) — рекомендуется ручная сверка перед отправкой во внешнюю организацию.
- Выбор T0 фиксирован (`ot_probsnr` с откатом на `ot`) — в отличие от `validate_associator_v2.py`, где доступны ещё `mean`/`wmean`/`probw`, здесь выбора через CLI нет.
- Захардкоженные однобайтовые коды (`analysis type`, `event type`, `pick type`, `onset quality`) отражают текущий уровень пайплайна (нет ручной верификации) — это не временные заглушки. `location method` — исключение: с 2026-09-13 переключается между `'o'` и `'i'` по факту наличия решения `core/locator.py` (`--locator-mode enrich|filter`), см. "Интеграция локатора" выше.
