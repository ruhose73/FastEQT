# cpu_pipeline.py — описание алгоритма

## Цель

Параллельно обрабатывает список станций (SEED → CSV детекций) **на CPU**, когда GPU недоступен или занят другой задачей. Собственной логики детекции не содержит — загружает `core/detector.py` через `importlib` и вызывает `process_station_v3()` для каждой станции; сам `cpu_pipeline.py` отвечает только за пул процессов, настройку TF под CPU-параллелизм и список станций/дат для конкретного прогона.

Модель, список станций, диапазон дат, число воркеров задаются флагами (`--help`); константы в начале файла остались как значения по умолчанию для этих флагов, конкретный прогон настраивается флагами, а не правкой файла. Более старая версия без CLI — `legacy/cpu_pipeline.py`.

---

## Отличие от `gpu_pipeline.py`

Единственная содержательная разница — способ работы с вычислительным устройством:

| | `cpu_pipeline.py` | `gpu_pipeline.py` |
|---|---|---|
| Устройство | `tf.config.set_visible_devices([], 'GPU')` — GPU принудительно скрыт от процесса | GPU используется, `set_memory_growth` |
| TF-параллелизм | `set_inter/intra_op_parallelism_threads(tf_threads)` на воркер, чтобы процессы не соревновались за ядра | не ограничивается — конкуренция за ядра CPU внутри GPU-режима не критична |
| `MAX_WORKERS` | подбирается под число CPU-ядер | подбирается под объём VRAM |

Остальное (диапазон дат, список станций, `estimate_uncertainty` включён или нет) — не структурная разница между файлами, а то, что настраивается под конкретную задачу флагами в обоих файлах одинаково; оба принимают `--date-from`/`--date-to`.

## Конфигурация — CLI-флаги (`--help`)

Константы с теми же именами остались в файле как значения по умолчанию.

| Флаг | Константа-дефолт | Назначение |
|---|---|---|
| `--model-path` | `MODEL_PATH` | путь к весам EQT (`.h5`), передаётся в `load_model_cudnn_v2` |
| `--output-base-dir` | `OUTPUT_BASE_DIR` | корневая директория, куда `process_station_v3` пишет CSV по каждой станции (`{OUTPUT_BASE_DIR}/{STATION}/{station}.csv`) — под какое поколение данных считать, определяется этим путём |
| `--max-workers` | `MAX_WORKERS` | число процессов `ProcessPoolExecutor` — сколько станций обрабатывается одновременно |
| `--tf-threads-per-worker` | `TF_THREADS_PER_WORKER` | сколько CPU-потоков TensorFlow разрешено использовать одному воркеру (`inter_op`/`intra_op` parallelism); произведение `--max-workers × --tf-threads-per-worker` — это то, сколько ядер реально задействовано одновременно, не должно намного превышать `os.cpu_count()`; `0` — подобрать автоматически (`max(1, os.cpu_count() // max_workers)`) |
| `--input-dir` / `--json-dir` | `_IN` / `_JS` | из них по кодам из `--stations` достраиваются пары `(входная_директория, station_*.json)` |
| `--stations` | `STATIONS` (пусто по умолчанию — см. ниже) | коды станций через запятую — какие обрабатывать в этом прогоне |
| `--date-from` / `--date-to` | `DATE_FROM` / `DATE_TO` | диапазон дат (строка, парсится через `UTCDateTime`), правая граница не включается |
| `--detection-threshold` / `--p-threshold` / `--s-threshold` / `--keep-ps` (`--no-keep-ps`) / `--allow-only-s` / `--sp-limit` / `--estimate-uncertainty` / `--number-of-sampling` / `--batch-size` | одноимённые константы | пороги предиктора и параметры MC Dropout, пробрасываются в `process_station_v3` (см. `detector.md`) — раньше часть из них была зашита прямо в `worker_v4` внутри `detector.py`, теперь настоящие параметры по всей цепочке |
| `--gap-mode {first-trace,merge}` | `first-trace` | суточный файл с разрывами: `first-trace` — как раньше, только до первого разрыва (`process_station_v3`); `merge` — склеить куски и обработать сутки целиком (`process_station_v4`). Выбор функции — в `run_station`, `gap_mode` — 7-й элемент кортежа задачи. Подробности и масштаб потерь — `detector.md`, раздел про `geofile_splitter_multi_chanels_v4` |

⚠️ **Дефолты MC Dropout здесь не такие, как в `gpu_pipeline.py`:** `--estimate-uncertainty` по умолчанию выключен, `--number-of-sampling` = 10 (в `gpu_pipeline.py` — включён, 5). Все рабочие прогоны проекта — с MC Dropout ×5, поэтому для сопоставимых результатов на CPU их нужно указывать явно: `--estimate-uncertainty --number-of-sampling 5` (см. `docs/server-run.md`).

`STATIONS` по умолчанию — пустая строка: в исходном файле (`legacy/cpu_pipeline.py`) все станции были закомментированы, при переносе на CLI это поведение сохранено буквально — без явного `--stations` список станций пуст, обрабатывать нечего.

**Рекомендации по `--max-workers`/`--tf-threads-per-worker` для машины с 12 ядрами** (из докстринга файла) — общий принцип: их произведение должно быть в районе числа ядер, а конкретное соотношение — компромисс между «больше параллельных станций» и «быстрее одна станция»:

| `--max-workers` | TF-потоков/воркер | Профиль |
|---|---|---|
| 4 | 3 | баланс скорость/параллелизм |
| 6 | 2 | больше параллельных станций |
| 8 | 1–2 | максимум параллельных станций, каждая станция обрабатывается медленнее |

## Как работает: initializer pattern

Загрузка модели — самая дорогая по времени операция, поэтому её выполняют один раз на процесс, а не один раз на станцию. Это достигается через `initializer` в `ProcessPoolExecutor`:

```python
ProcessPoolExecutor(max_workers=MAX_WORKERS,
                     initializer=_init_worker,
                     initargs=(MODEL_PATH, tf_threads))
```

1. **`_init_worker(model_path, tf_threads)`** — выполняется один раз, сразу при старте каждого процесса-воркера (ещё до того, как ему назначат первую станцию):
   - добавляет `_ROOT` (корень репозитория) в `sys.path` — процесс-воркер запускается как отдельный интерпретатор Python и не наследует изменения `sys.path`, сделанные родительским процессом после старта;
   - `tf.config.set_visible_devices([], 'GPU')` — скрывает GPU для этого процесса;
   - ограничивает TF-потоки (`tf_threads`), чтобы несколько воркеров не конкурировали за одни и те же ядра CPU;
   - загружает `core/detector.py` через `importlib.util.spec_from_file_location` (функция `_load_detector()`), а не обычным `import detector` — так каждый процесс получает собственный экземпляр модуля, независимо от того, как проект установлен/на каком уровне лежит;
   - загружает модель один раз через `detector.load_model_cudnn_v2(model_path)` и сохраняет её в глобальную переменную `_model` — эта же модель переиспользуется для всех станций, которые попадут именно в этот процесс.
2. **`run_station(args)`** — функция-задача, отправляется в пул через `executor.submit()` один раз на каждую станцию из списка, построенного по `--stations`:
   - вызывает `_detector_mod.process_station_v3(...)` с уже разобранными `date_from`/`date_to` (`--date-from`/`--date-to`, распарсены через `UTCDateTime` до запуска пула) и порогами из CLI-флагов, передавая уже загруженную модель `_model` (глобальную переменную процесса, а не аргумент, полученный из основного процесса — модель нельзя сериализовать между процессами, поэтому паттерн именно «загрузить внутри воркера один раз», а не «загрузить один раз в родителе и передать всем»);
   - любое исключение перехватывается целиком и возвращается как `(station_name, "error", traceback.format_exc())` — ошибка на одной станции не прерывает обработку остальных: основной цикл `for future in as_completed(...)` продолжает получать результаты по мере готовности.

## Что делает `process_station_v3` (внутри `core/detector.py`)

И `cpu_pipeline.py`, и `gpu_pipeline.py` вызывают одну и ту же функцию — вся специфика собственно детекции живёт в `detector.py`, а не здесь. Коротко, что происходит внутри одного вызова на одну станцию:

1. **`geofile_splitter_multi_chanels_v3(base_directory, date_from, date_to)`** — генератор: находит файлы по имени (`NET.STA.LOC.CHA__start__end`, формат из `data_processors/geofile_processor.py`), отбирает попадающие в `[date_from, date_to)` (правая граница не включена), нарезает поток на 10-минутные сегменты с шагом 5 минут (50% перекрытие между соседними сегментами — эталон, на котором обучался EQT).
2. **`preproc_sequential_v5(...)`** — потребляет генератор последовательно: берёт сегмент, передаёт в обработку, сразу пишет результат в CSV, удаляет сегмент из памяти, переходит к следующему (не накапливает весь месяц в памяти сразу); `gc.collect()` каждые 50 сегментов.
3. На каждый сегмент вызывается **`worker_v4`**, который:
   - вызывает `preprocessorV7_mem` — предобработка (детрейд, тейпер, ресемплинг до 100 Гц, фильтрация) с корректным ресемплингом через `st.resample()` (в отличие от более старой `preprocessorV6_mem`, которая растягивала массив через `np.interp`);
   - вызывает `predictor_mem_non_hdf_load_model_v6` с порогами `detection_threshold/P_threshold/S_threshold/keepPS/allowonlyS/spLimit/batch_size` — настоящими параметрами по всей цепочке, задаются флагами `--detection-threshold`/`--p-threshold`/`--s-threshold`/`--keep-ps`(`--no-keep-ps`)/`--allow-only-s`/`--sp-limit`/`--batch-size` (см. `detector.md`).
4. **`estimate_uncertainty`/`number_of_sampling`** (флаги `--estimate-uncertainty`/`--number-of-sampling`) — параметры `process_station_v3`, пробрасываются до `predictor_mem_non_hdf_load_model_v6`. При `estimate_uncertainty=True` модель вызывается `number_of_sampling` раз в режиме `model(X, training=True)` (реальный MC Dropout, не косметический — см. правило №8 в `CLAUDE.md`) вместо одного `model.predict()`, и в CSV дополнительно попадают `detection_uncertainty`/`p_uncertainty`/`s_uncertainty` — их затем использует `core/associator.py` в режимах `UNCERTAINTY_MODE='weight'`/`'filter'`.

## Вывод и логи

- По мере готовности каждой станции печатается: `[elapsed мин] [STATUS] station_name`; при ошибке — первые 800 символов traceback.
- В конце — сводка: число успехов/ошибок, число ядер, использованных воркеров, общее время.
- `preproc_sequential_v5` дополнительно пишет отдельный лог по сегментам в `LOG_FILE` (`workspace/detector/output/processing_log.csv`, константа **в `detector.py`**) — в режиме перезаписи (`'w'`), не дописывает.

**Гонка при параллельной обработке:** лог сегментов (`--log-file` в `detector.py`, по умолчанию `workspace/detector/output/processing_log.csv`) — один общий путь для всех воркеров, не per-станция. При `--max-workers > 1` несколько процессов пишут в этот же файл конкурентно, каждый перезаписывает его целиком по завершении своей станции — в итоге в файле остаётся лог только той станции, чей процесс закончил последним, логи остальных станций теряются молча (без ошибки). Основной CSV с детекциями (`{OUTPUT_BASE_DIR}/{STATION}/{station}.csv`) этой проблемы не имеет — он per-станция и per-процесс не конфликтует.
