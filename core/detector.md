# detector.py — описание алгоритма

## Цель

Центральный модуль детекции: читает суточные SEED-файлы одной станции, нарезает их на перекрывающиеся 10-минутные сегменты, прогоняет через модель EQTransformer и пишет один CSV с детекциями (детекция + P/S-пики, с вероятностями и SNR, опционально MC Dropout неопределённость) на станцию. Полностью автономен — не импортирует ничего из `legacy/` и не зависит от `cutter-v5.py`; единственные внешние зависимости — сам пакет `EQTransformer/`.

Файл используется **двумя разными способами**, но обе — одна и та же цепочка обработки (`process_station_v3`, см. ниже):
1. **Напрямую** — `python core/detector.py --stations ... [--date-from/--date-to ...]`: обрабатывает список станций (из `--stations`, по умолчанию — сегодняшний список) последовательно, одним процессом, одной уже загруженной моделью.
2. **Как библиотека** — `core/cpu_pipeline.py` и `core/gpu_pipeline.py` загружают его через `importlib` и вызывают `process_station_v3()` из нескольких процессов параллельно (`ProcessPoolExecutor`), каждый процесс — со своей копией модели. Сам `detector.py` пулом процессов не управляет — это исключительно забота вызывающих pipeline-файлов.

## История: было две цепочки, осталась одна

**Единственная цепочка обработки сегмента.** Более старая версия файла содержала вторую цепочку (`process_station` → `preproc_sequential_v4` → `worker_v3` → `preprocessorV6_mem`, без MC Dropout, только для прямого `__main__`-запуска) — небезопасную для станций с частотой дискретизации <90 Гц: `preprocessorV6_mem` ресемплировала **после** фильтрации (растяжение массива `np.interp`, а не `st.resample()`), из-за чего ObsPy молча подставлял high-pass 1 Гц без верхней границы вместо полосового фильтра 1–45 Гц (8 из 10 проверенных станций текущей сети имеют частоту <90 Гц — не редкий случай; проверено эмпирически, см. `EQTransformer/eqt_internals.md`, разд. 3). Эта цепочка удалена; предыдущая версия файла — `legacy/detector.py`.

Что именно изменилось:
- `geofile_splitter_multi_chanels_v2`, `worker_v3`, `preproc_sequential_v4`, `process_station` удалены из `core/detector.py`.
- `EQTransformer/` **не тронут** (правило №1 `CLAUDE.md` — не форк/апдейты EQTransformer, только код проекта): `preprocessorV6_mem` (`EQTransformer/utils/hdf5_maker.py`) и `predictor_mem_non_hdf_load_model_v4` (`EQTransformer/core/predictor.py`) остались на месте, просто `core/detector.py` их больше не импортирует и не вызывает.
- `__main__` пересобран поверх `process_station_v3` — той же самой цепочки, что использует `cpu_pipeline.py`/`gpu_pipeline.py`. Прямой запуск `python core/detector.py` теперь принимает `--date-from`/`--date-to` вместо `--month`/`--year` (сигнатура `process_station_v3` — даты, не месяц/год; заодно унификация с `cpu_pipeline.py`/`gpu_pipeline.py`), плюс `--estimate-uncertainty`/`--number-of-sampling`.
- Единственный внешний потребитель старой цепочки — `plot_event.py` (временный скрипт в корне репозитория, строит графики детекций для одного события) — переведён на `geofile_splitter_multi_chanels_v3`/`preproc_sequential_v5`.
- Предыдущая версия файла (с обеими цепочками) — `legacy/detector.py`.

## Загрузка модели и cuDNN-патч

### `load_model_cudnn_v2(model_path)` + `_patch_lstm_inplace(model)`

Модель EQTransformer использует LSTM-слои; чтобы TensorFlow на GPU использовал быстрый cuDNN-kernel вместо обычной реализации, LSTM-слой должен удовлетворять ряду условий (в частности `recurrent_dropout=0.0`, `implementation=2`). Проблема: `recurrent_dropout` и `implementation` — **read-only свойства** (`@property`) на самом LSTM-слое, их нельзя присвоить напрямую после загрузки. Но эти же значения хранятся как обычные атрибуты на `lstm.cell` (объект `LSTMCell`), и туда присвоение работает.

`_patch_lstm_inplace`:
- проходит по всем слоям модели;
- для `Bidirectional`-обёрток берёт оба вложенных LSTM (`forward_layer`, `backward_layer` — направление вперёд и назад по времени, обе половины нужно патчить отдельно);
- на каждом найденном LSTM-слое (прямом или из `Bidirectional`) присваивает `lstm.cell.recurrent_dropout = 0.0` и `lstm.cell.implementation = 2`.

`load_model_cudnn_v2` — обёртка вокруг этого: `load_model(..., compile=False)` → патч → `model.compile(...)`. Patch применяется **после** загрузки и **до** первого вызова `predict()`/`model()` — на этапе `load_model` при трассировке графа неизбежно печатается предупреждение о несовместимости с cuDNN (косметическое, см. правило №4 в `CLAUDE.md`), но после патча реальный inference уже идёт через cuDNN kernel, повторного предупреждения при `predict()` не возникает.

Более ранняя версия (`load_model_cudnn`, без суффикса, не в этом файле — см. `CLAUDE.md`, помечена неактивной) пыталась пересобрать модель через `model_from_json` с изменённым конфигом; в TF 2.10 это не работало для `Bidirectional`-слоёв — конфиг игнорировался при десериализации. Патч на уже созданных объектах — рабочий обход этой проблемы.

## Нарезка на сегменты: `geofile_splitter_multi_chanels_v3`

Генератор (не список): обрабатывает файлы одной станции по очереди, отдаёт сегменты через `yield`, не загружая весь диапазон в память сразу.

1. Все файлы каталога станции разбираются регэкспом `NET.STA.LOC.CHA__start__end` (формат из `data_processors/geofile_processor.py`).
2. Файлы группируются по ключу `{STA}_{start}` — то есть все каналы (`BHE`, `BHN`, `BHZ`, ...), относящиеся к одному и тому же суточному файлу одной станции, попадают в одну группу (обычно 2–3 файла на группу, по одному на канал).
3. Файлы группы читаются в один `Stream` (`st_all += read(fpath)`). Если в группе меньше 2 каналов после чтения — группа пропускается (недостаточно компонент для детекции).
4. Проверяется попадание `start_time` первого канала в `[date_from, date_to)` (правая граница не включена).
5. Поток нарезается на 10-минутные окна (`window_length = 600s`) с шагом 5 минут (`step = 300s`, то есть 50% перекрытие между соседними сегментами — тот же формат окон, на котором обучался сам EQTransformer). Каждое окно, где не меньше 2 каналов и во всех есть отсчёты, отдаётся через `yield (segment, seg_name)`.
6. После последнего полного шага отдельно проверяется и добавляется «хвостовой» сегмент — последние 10 минут потока (`end_time - window_length .. end_time`), если он не совпал с уже отданными окнами (`t < end_time`) — иначе конец суточного файла не попал бы ни в одно окно из-за целочисленного шага.
7. `st_all` явно удаляется (`finally: del st_all`) после каждой группы — пиковое потребление памяти: один суточный поток + один обрабатываемый сегмент, не весь диапазон целиком.

⚠️ **Баг v3: суточный файл с разрывом обрабатывается только до первого разрыва.** Конец нарезки (`end_time`) берётся у первого куска первой трассы (`st_all[0].stats.endtime`). Если в суточном файле есть хотя бы один разрыв записи (канал = несколько трасс), всё после него в окна не попадает. Разрывы короткие (секунды, максимум ~85 с), но остаток суток теряется целиком. Май 2024 (56 станций): затронуто 214 станцие-суток из ~1 510, не обработано ~10% всех станционных данных; по станциям — PXTR 70%, URKR 59%, UNCR 49%, DBC 37%, DRN 31%, AKT 17%. Пример: AKT 17.05.2024 — разрыв 52 с в 12:46:57, после него 11 ч не обработано, в том числе событие M4.5 15:31 в 35 км. Функция оставлена как есть (правило 13 `CLAUDE.md`), исправление — v4 ниже.

### `geofile_splitter_multi_chanels_v4` (`--gap-mode merge`)

Как v3, с двумя отличиями:

1. Куски каждого канала склеиваются: `st_all.merge(method=1, fill_value='interpolate')` — разрыв заполняется линейной интерполяцией (без ступенек на краях, которые полосовой фильтр превратил бы в ложные детекции).
2. Окна идут по всему диапазону суток: `[min starttime, max endtime]` по всем каналам, а не по первому куску.

Если `merge` падает (например, куски с разной частотой дискретизации) — группа обрабатывается как в v3, с предупреждением в выводе. Фильтр по датам — тот же, что в v3 (по началу первой трассы суточного файла), поэтому `--date-from`/`--date-to` работают с точностью до суток: время внутри суток не отрежет сегменты.

Проверено: AKT 17.05.2024 — 288 сегментов вместо 153, появилась детекция P 15:31:28.84 / S 15:31:32.87 (бюллетень ГС РАН: 28.84 / 32.86); то же получено через `cpu_pipeline.py --gap-mode merge` на CPU.

## Обработка сегмента: `worker_v4`

Логирует начало обработки сегмента, засекает время предобработки и время инференса отдельно, ловит любое исключение целиком и возвращает `(seg_name, status, message, rows)` — ошибка на одном сегменте не должна прерывать обработку всего диапазона у станции.

`worker_v4` → `preprocessorV7_mem` (предобработка: детренд/тейпер/фильтрация/приведение к общей частоте — ресемплинг через `st.resample()`, корректный FFT-метод с антиалиасингом) → `predictor_mem_non_hdf_load_model_v6`, с параметрами `estimate_uncertainty`/`number_of_sampling`, проброшенными снаружи (от `process_station_v3` до сюда).

Пороги предиктора (`detection_threshold`/`P_threshold`/`S_threshold`/`keepPS`/`allowonlyS`/`spLimit`/`batch_size`) — настоящие параметры функции, поднятые по всей цепочке (`worker_v4 → preproc_sequential_v5 → process_station_v3`) до CLI-флагов; раньше были зашиты прямо в теле `worker_v4`. `EQTransformer/` не тронут — сигнатура `predictor_mem_non_hdf_load_model_v6` эти параметры уже принимала, менялся только `core/detector.py`.

### MC Dropout

Dropout-слои в Keras по умолчанию **выключены** во время инференса (`model.predict()` / вызов модели без `training=True`) — это стандартное поведение, не баг. «MC Dropout» (Monte Carlo Dropout) — способ оценить неопределённость предсказания, оставляя dropout **включённым** во время инференса и прогоняя один и тот же вход несколько раз: разные случайные маски dropout на каждом проходе дают разброс предсказаний, чей разброс (std) и есть оценка неопределённости.

`predictor_mem_non_hdf_load_model_v6` реализует это по-настоящему: внутренняя функция `_mc_forward` вызывает `model(batch, training=True)` — dropout активен, `number_of_sampling` проходов (флаг `--number-of-sampling`) дают разные результаты, откуда и берётся ненулевой std для `detection_uncertainty`/`p_uncertainty`/`s_uncertainty`. Именно так эти столбцы попадают в `CSV_HEADER` осмысленными числами, а не нулями (см. правило №8 `CLAUDE.md`: `estimate_uncertainty=True` без реального `training=True`-прохода — чисто косметический флаг, std всегда ≈0). Включается флагом `--estimate-uncertainty`, по умолчанию выключен (в `cpu_pipeline.py`/`gpu_pipeline.py` дефолты могут отличаться — см. их `.md`).

## Драйвер по сегментам: `preproc_sequential_v5`

Вызывается **один раз на станцию** (не на сегмент) и сама итерирует переданный генератор сегментов до конца:

1. Открывает `output_csv` (`'w'`, с нуля) и сразу пишет заголовок `CSV_HEADER`.
2. Для каждого сегмента из генератора вызывает `worker_v4`, сразу пишет вернувшиеся строки в CSV и делает `flush()` (детекции появляются в файле по ходу обработки, не только в самом конце — если процесс упадёт на середине диапазона, часть результатов уже на диске).
3. Сегмент явно удаляется (`del segment`) сразу после обработки; каждые 50 обработанных сегментов — `gc.collect()` с логом числа найденных на этот момент событий.
4. По завершении генератора — ещё раз `gc.collect()`, затем **перезаписывается** (`'w'`) лог (`--log-file`) со списком `(seg_name, status, message, n_events)` по всем сегментам этой станции.

⚠️ **Лог по сегментам — один путь на весь прогон, не per-станция.** Функция открывает его в режиме перезаписи по завершении обработки одной станции. Если несколько станций обрабатываются в параллельных процессах (как это делают `cpu_pipeline.py`/`gpu_pipeline.py` через `ProcessPoolExecutor`), каждый процесс независимо перезаписывает один и тот же файл по завершении своей станции — в итоге в логе остаётся запись только той станции, чей процесс закончил последним; логи остальных станций молча теряются (без ошибки). Сам CSV с детекциями (`{output_base_dir}/{STATION}/{station}.csv`) этой проблемы не имеет — он per-станция.

## Точка входа по станции: `process_station_v3`

Тонкая обёртка: вычисляет `output_csv = {output_base_dir}/{STATION}/{station_lower}.csv` по имени папки станции, создаёт генератор сегментов (`geofile_splitter_multi_chanels_v3`) и передаёт его в `preproc_sequential_v5`. Принимает `date_from`/`date_to` (`UTCDateTime`). Используется и `__main__` (прямой запуск), и `core/cpu_pipeline.py`/`core/gpu_pipeline.py` (параллельный запуск).

`process_station_v4` — то же самое, но генератор сегментов — `geofile_splitter_multi_chanels_v4` (суточный файл с разрывами обрабатывается целиком). Какую из двух вызывать, выбирает флаг `--gap-mode` (`first-trace` → v3, `merge` → v4) — одинаково в `detector.py`, `cpu_pipeline.py`, `gpu_pipeline.py`.

## Конфигурация — CLI-флаги (`--help`)

Все параметры прямого запуска (`python core/detector.py`) — флаги командной строки, не константы в коде. Константы с теми же именами остались в файле как значения по умолчанию для этих флагов.

| Флаг | Константа-дефолт | Назначение |
|---|---|---|
| `--model-path` | `MODEL_PATH` | путь к весам EQT (`.h5`) |
| `--output-base-dir` | `OUTPUT_BASE_DIR` | куда `process_station_v3` пишет CSV по станциям |
| `--log-file` | `LOG_FILE` | общий путь лога по сегментам, перезаписывается на каждый вызов `preproc_sequential_v5` (см. предупреждение выше) |
| `--input-dir` / `--json-dir` | `_IN` / `_JS` | из них по кодам из `--stations` достраиваются пары `(входная_директория, station_*.json)`, как раньше делал список `STATIONS` |
| `--stations` | `STATIONS` (строка кодов через запятую) | какие станции обработать при прямом запуске через `__main__` |
| `--date-from` / `--date-to` | `DATE_FROM` / `DATE_TO` | диапазон дат (строка, парсится через `UTCDateTime`), правая граница не включается |
| `--estimate-uncertainty` / `--number-of-sampling` | `ESTIMATE_UNCERTAINTY` / `NUMBER_OF_SAMPLING` | MC Dropout (см. выше) |
| `--detection-threshold` / `--p-threshold` / `--s-threshold` / `--keep-ps`(`--no-keep-ps`) / `--allow-only-s` / `--sp-limit` / `--batch-size` | одноимённые константы | пороги предиктора (см. выше) |
| `--gap-mode {first-trace,merge}` | `first-trace` | суточный файл с разрывами: `first-trace` — старое поведение, только до первого разрыва (`process_station_v3`); `merge` — склеить куски и обработать сутки целиком (`process_station_v4`) |
| `CSV_HEADER` (не CLI) | — | список колонок выходного CSV (детекция + P/S пики, вероятности, uncertainty, SNR) |

При переносе на CLI также добавлен `sys.path.insert(0, _ROOT)` перед импортом `EQTransformer` (как в `core/associator.py`) — без него `python core/detector.py --help` падал на импорте, потому что при прямом запуске в `sys.path` попадает папка `core/`, а не корень проекта; раньше это не было заметно, так как файл всегда запускали через `cpu_pipeline.py`/`gpu_pipeline.py`, которые сами делают эту вставку перед загрузкой файла через `importlib`.

## `__main__`: строго последовательный

`__main__` этого файла не создаёт `ProcessPoolExecutor` — обычный `for bd, sj in stations: process_station_v3(...)` в одном процессе с одной моделью, загруженной один раз до цикла. Параллельный `initializer`-паттерн реализован не здесь, а в `core/cpu_pipeline.py` и `core/gpu_pipeline.py`, которые загружают этот файл через `importlib` и сами создают `ProcessPoolExecutor`, каждый процесс грузит свою копию модели через `load_model_cudnn_v2` и вызывает ту же самую `process_station_v3()`. Иными словами: если нужен параллельный запуск нескольких станций, использовать нужно не `python core/detector.py`, а один из pipeline-файлов — разница только в параллелизме, не в алгоритме.

`__main__` также настраивает `set_memory_growth` для GPU и оборачивает каждый вызов `process_station_v3` в `try/except`, чтобы ошибка на одной станции не остановила обработку остальных (аналогично `run_station` в pipeline-файлах, но без промежуточного слоя воркеров — всё в одном процессе, последовательно).
