# ml_filter_v5.py — описание алгоритма

## Цель

Фильтрует `associations.xml` ассоциатора, оставляя только события с локальной магнитудой ML выше порога. Работает полностью в памяти: читает MSEED-файлы оконно, снимает инструментальный ответ, кэширует амплитуды в CSV. Обрабатывает **все** события XML (в отличие от `legacy/ml_filter_v3.py`, который работал на выборке для быстрого подбора порога).

## Отличие от `ml_filter_v4.py`

`v5` не меняет алгоритм по сравнению с `v4` — для одного и того же входа и одинаковых значений параметров оба считают ML идентично. Изменения:

1. **Убран мёртвый legacy-путь агрегации** — `compute_event_ml` + `_filter_by_amp_ratio` (итеративный ratio-фильтр по амплитуде, путь v1/v3). В `v4` он не вызывался из `main()` и был достижим только вручную, через `print_diag_event(..., use_v2=False)`, то есть только для сравнения при диагностике одного события. Рабочий путь всегда был один — `compute_event_ml_v2` (медиана → σ-фильтр выбросов → среднее); он и остался единственным в `v5`. Параметр `use_v2` в `print_diag_event` убран вместе с веткой.
2. **Все константы формулы/порогов/окон переведены в CLI-флаги.** В `v4` `ML_B_LOG`, `ML_B_LIN`, `ML_C`, `R_MIN_KM`, `R_MAX_KM`, `WIN_SEC`, `READ_MARGIN_SEC`, `MAX_GROUP_SPAN_SEC`, `BP_FREQMIN`/`BP_FREQMAX`, `A_NM_MIN`, `A_MAX_NM`, `N_MIN_STA`, `ML_OUTLIER_SIGMA`, приоритет компонент — были хардкод-константами в начале файла, недоступными без правки кода. В `v5` каждая — CLI-флаг; значения по умолчанию **не изменились**, поведение без флагов идентично `v4`.
3. **`AMP_SCALE_NM` (м → нм, ×1e9) в CLI не вынесен** — это не настраиваемый порог, а фиксированный перевод единиц (метры на выходе `remove_response` в нанометры для формулы), константа `AMP_SCALE_NM` осталась в коде.
4. **Мелкая правка в `--diag-pubid`.** В `v4` построчный статус выброса в диагностике всегда печатал текст `>2σ=...`, даже если реальный множитель (`ML_OUTLIER_SIGMA`) отличался от 2 (по умолчанию 1.5) — метка не совпадала со значением. В `v5` в статусе подставляется настоящее переданное значение `--ml-outlier-sigma`.

`ml_filter_v4.py` при этом не удалён и не изменён — перенесён в `legacy/ml_filter_v4.py` (`legacy/ml_filter_v4.md` — тот же текст описания, что и раньше) как исторический снимок кода до чистки, а не оставлен рядом с `v5` в `core/`; для новых запусков используйте `v5`.

## Формула ML (Дягилев et al. 2023, формула 5б)

```
ML = lg(A_нм) + b_log·lg(R) + b_lin·R + c + S
```

| Член | По умолчанию | CLI | Физический смысл |
|---|---|---|---|
| `lg(A_нм)` | — | — | логарифм пикового смещения грунта в нанометрах — мера амплитуды S-волны на станции |
| `b_log·lg(R)` | `b_log=1.024` | `--ml-b-log` | геометрическое расхождение: амплитуда убывает как ~1/R при распространении |
| `b_lin·R` | `b_lin=0.001648` | `--ml-b-lin` | неупругое затухание: экспоненциальное поглощение энергии в среде |
| `c` | `c=-1.889` | `--ml-c` | константа калибровки формулы для Терско-Каспийского прогиба |
| `S` | `0` | `--sta-corrections` | станционная поправка — компенсирует локальные геологические условия под станцией |

Расстояние R вычисляется не по координатам гипоцентра, а по S-P формуле:

```
R = Vp·Vs / (Vp − Vs) · ΔT(S-P)
```

где `ΔT = t_S − t_P` в секундах, `Vp=6.0`, `Vs=3.4883` км/с (оба настраиваются через `--vp`/`--vs`), что даёт коэффициент `k ≈ 7.84` км/с. Это позволяет не использовать гипоцентральную локацию — достаточно пиков P и S из ассоциатора. Событие без S-пика на станции (нет `ΔT`) в расчёт R для этой станции не попадает — станция просто выпадает из списка для этого события (`compute_r_dict`).

### `--distance-source {sp,locator}` — реальная дистанция вместо S-P-оценки (раздел 1.7d плана, 2026-09-13)

По умолчанию (`sp`) `R` вычисляется по формуле выше — поведение не меняется. `--distance-source locator` вместо этого берёт **реальную** дистанцию из `--hypocenters` (выход `core/locator.py`, LOCSAT) через `compute_r_dict_from_locator()`, но только для событий с сошедшимся решением (`converged=True`); событие без решения (или отсутствующее в файле) автоматически откатывается на `compute_r_dict()` (S-P) в этом же прогоне — не ошибка, просто фолбэк (см. в выводе `R из локатора: N  fallback на S-P: M`).

`--locator-distance-metric {hypocentral,epicentral}` (default `hypocentral`) — какую величину считать за `R`:
- `hypocentral` (default): `R = sqrt(эпицентральная² + depth_km²)` — та же физическая величина, что фактически даёт S-P-формула выше (S-P время зависит от полной длины луча, не только от горизонтальной дистанции) — так ML между `sp`/`locator` остаётся сравнимым, не меняя молча калибровку формулы Дягилева.
- `epicentral`: только горизонтальная дистанция, без глубины.

Координаты станций читаются отдельным лёгким загрузчиком `load_station_coords(--metadata-dir)` (ElementTree по StationXML, независимо от полновесного ObsPy `Inventory`, который этот модуль грузит только при промахе кэша амплитуд, — координаты нужны всегда при `locator`, вне зависимости от того, попал ли кэш). `load_hypocenters(--hypocenters)` — независимая копия того же формата, что в `core/export_bul.py`/`core/validate_associator_v2.py` (Rule 14: намеренное дублирование между независимыми потребителями, не унифицировано — эти модули не импортируют друг друга).

## `--ml-stations consistent` и `--max-station-dist-km` (2026-10-07)

**Проблема.** Ассоциатор подмешивает в событие пики чужих станций. У такой станции разница S-P маленькая, `R` по S-P получается в 10–30 раз меньше истинного, ML станции сильно занижена — и тянет вниз ML события. Хуже того, самая сильная своя станция на этом фоне выглядит выбросом и отбрасывается σ-фильтром. Май 2024: шесть реальных событий с MPVA 3.1–4.5 по бюллетеню ГС РАН получили ML 0.96–1.47 и были удалены фильтром ≥ 1.5; ML только по своим станциям у них 2.1–3.1.

**`--ml-stations consistent`.** Для каждого события сначала отбираются станции с согласованным временем очага T0 — `consistent_stations()`, тот же σ-фильтр, что в `validate_associator_v2.py` (`estimate_origin_times` + `sigma_filter`, импорт, а не копия; `--consistency-sigma`, по умолчанию 1.0; станции ближе 20 км в оценку T0 не входят). ML считается только по ним (`compute_event_ml_v3()`). Если так ML не получается (меньше `--n-min-sta` станций с амплитудой) — для этого события откат на ML по всем станциям. В выводе: сколько событий посчитано по согласованным станциям и сколько с откатом. Амплитуды те же (кэш не пересчитывается).

**`--max-station-dist-km`.** Станции дальше этого расстояния от `--ref-lat/--ref-lon` (по умолчанию Сочи) исключаются и из ML, и из T0-фильтра — **до** него, иначе чужие дальние станции могут оказаться «согласованным большинством». Координаты — из `--station-coords-json` (сводный JSON `data_processors`), недостающие — из StationXML `--metadata-dir`. Станции без координат **не отсекаются**, скрипт печатает их список с предупреждением — их нужно дописать в JSON.

**Проверено против бюллетеня ГС РАН** (`export_bul.py` → `compare_bul.py --min-mag 1.5`, recall при ≥ 4 / ≥ 1 общих станциях; май 2024 — этими флагами, 2025 — эквивалентным скриптом, т.к. координат дальних станций 2025 года пока нет в JSON):

| Период | `all` (как раньше) | `consistent` + без дальних станций |
|---|---|---|
| Май 2024 (46) | 36 / 37, 548 событий | **38 / 39**, 543 |
| 2025 Q1 (112) | 71 / 81, 3 561 | 71 / 81, 2 851 |
| 2025 апрель (33) | 14 / 19 | **15** / 18 |
| 2025 май–июнь (56) | 38 / 42 | **39 / 43** |
| Итого (247) | 159 / 179, 8 582 событий | **163 / 181**, 6 952 (−19%) |

Апрель 2025 при ≥ 1 станции −1 — от исключения дальних станций, не от `consistent`. Вариант «только согласованные станции без отката» проверялся и отброшен: на 2025 году теряет реальные события (Q1: 61 вместо 71).

Без новых флагов поведение побайтово прежнее (проверено сравнением выходного XML до и после правки).

## `--ml-stations p-traveltime` — отбор станций по P-годографу (2026-10-11)

**Проблема, которую `consistent` не решает.** Май 2024, два события MPVA 3.4 и 3.1 (12.05 23:26, 27.05 16:58): ассоциатор собрал свои станции, но (1) в событие вошли чужие в 400–900 км, чьи P пришли *раньше*, чем волна могла до них дойти; (2) на части своих станций EQT поставил S на фазу сразу за P (S-P 1–2 с на 110–200 км), R по S-P в ~10 раз меньше истинного — своя станция выпадает по `R < 20 км`. σ-фильтр T0 сам считается по S-P, поэтому «согласованным большинством» оказываются чужие. ML события ~1.0 вместо ~2.1. Отбор по географии (радиус) и LOCSAT это не лечат (проверено 2026-10-09).

**Метод — «вслепую»:** только пики события, координаты станций и региональный годограф P, без места события и бюллетеня.

1. **Годограф первой P** — `--tt-table`, CSV из `core/fit_traveltime.py` (медиана tP по бинам 10 км). Поставляемый `core/data/tt_p_ncau2024.csv` — бюллетень ГС РАН NCAU 2024 **без мая** (май — проверочный), 9 451 пара событие-станция: 100 км ≈ 19 с, 200 км ≈ 34 с, 300 км ≈ 46 с, разброс ±1.5–2 с. Используются бины с ≥ `--tt-min-n` (20) пар, т.е. до 415 км; дальше — продолжение со скоростью 8 км/с.
2. **Перебор эпицентра** по сетке `--ptt-grid` (39–47°N × 36–50°E, шаг 0.1°, 11 421 узел; `PTravelTimeLocator.locate()`). В узле T0_i = P_i − tP(d_i); «свои» — станции, чьи T0 в ±`--ptt-p-tol` (2.5 с) от T0 станции-якоря; узел и якорь — максимум своих (при равенстве — минимум суммы невязок). Станции из `--exclude-stations`/`--max-station-dist-km` и без координат в локации не участвуют. Своих меньше `--ptt-min-stations` (4) → событие считается как `consistent`.
3. **Уточнение точки** при фиксированных своих: минимум дисперсии T0 по P своих и по S своих (tS = Vp/Vs · tP); S-пик участвует, только если его T0 в ±8 с, затем ±3 с от T0 по P (`--ptt-s-tol`) — S «сразу за P» отпадает сам. Без S точка уезжала на ~60 км наружу сети.
4. **Подтверждение очага S.** Своя станция «подтверждает», если её R по S-P согласуется с R от точки (глубина фиксирована `--ptt-depth-km` 15 км): |ΔR| ≤ max(`--ptt-r-tol-km` 30 км, `--ptt-r-tol-frac` 30%). Подтверждающих меньше `--ptt-n-confirm` (2) → событие считается как `consistent` (`compute_event_ml_v3`).
5. **Подтверждён** → ML только по своим станциям; расходящийся R_sp заменяется R от точки (если ≤ `--r-max-km`). Если по своим ML не получился (< `--n-min-sta` с амплитудой) — откат на ML по всем станциям (как в `compute_event_ml_v3`).

Без подтверждения S (шаг 4) метод раздувает выдачу в ~20 раз (май: 15 036 событий вместо 681) — у шумовых «событий» случайные P тоже ложатся на годограф. Поэтому подтверждение обязательно и отключить его флагом нельзя. Вариант «выбросить станцию с расходящимся R_sp» вместо замены R был нейтрален (40/46).

В выводе — разбивка событий: подтверждено (ML по своим) / подтверждено, но ML по всем / не подтверждено / не локализовано (два последних — как `consistent`). Май 2024 merge_p6: 368 / 87 / 20 081 / 2 134 из 22 670. Скорость ~15 мс на событие (весь май ~5 мин на кэше амплитуд). Амплитуды те же, кэш не пересчитывается — второй прогон на том же `--cache-amp` с другим `--assoc-out`.

Режим включает в себя `consistent`: события без подтверждения считаются ровно так же, поэтому флаги `--consistency-sigma`, `--max-station-dist-km` и т.д. действуют и здесь.

**Проверено против бюллетеня ГС РАН** (`compare_bul.py --min-mag 1.5`, recall при ≥ 4 общих станциях; база — `consistent --max-station-dist-km 800`; прототип `context/scratch/ml_ptt.py conf`, перенос в `core/` проверен побайтово на мае):

| Данные | `consistent` | `p-traveltime` | Выдача | Добавлены (MPVA) |
|---|---|---|---|---|
| Май 2024, полный (merge_p6) | 40/46 | **42/46** | 681 → 752 (+10%) | 12.05 23:26 (3.4), 27.05 16:58 (3.1) |

| Апрель 2024 (старые детекции без MC) | 17/20 | **18/20** | 7 485 → 9 047 (+21%) | 25.04 10:41 (2.9) |
| 2025 Q1 (старый прогон, 81 станция) | 71/112 | **74/112** | 2 844 → 3 001 (+5.5%) | 14.01 (3.1), 27.02 (4.3), 28.03 (4.5) |

Лишние события в мае (+75 с ML ≥ 1.5, −7) — почти все с ML 1.5–1.8 и минимальным подтверждением (2 станции); ужесточения («≥ 5 своих», «≥ 3 подтверждающих») не приняты — подгонка под 2 события, без проверки на других данных.

### `--out-xml-ptt` — вход для `core/locator.py` (2026-10-11)

Те же «свои» станции — как вход LOCSAT вместо `validate_associator_v2.py --out-xml-inliers` (`write_quakeml_ptt()`). Пишется дополнительно к основному выходу, для событий, прошедших порог ML: P всех своих станций + S только тех, чьё R по S-P согласно с точкой перебора (критерий шага 4; S «сразу за P» в LOCSAT не попадает), начальное приближение `origin` — точка перебора и T0 по P. publicID события тот же, `hypocenters.csv` стыкуется с `export_bul.py --locator-mode enrich`. Нелокализованные события не пишутся (в бюллетене остаются без координат). Работает при любом `--ml-stations`, параметры — те же `--ptt-*`/`--tt-table`.

Порядок: `ml_filter_v5.py ... --out-xml-ptt X.xml` → `locator.py --assoc X.xml` (WSL, `seiscomp-python`) → `export_bul.py --locator-mode enrich --hypocenters ...` → `compare_bul.py --location-error`.

Проверено (LOCSAT с глобальной iasp91; одинаковые события после ML `p-traveltime`; «хорошее» — Err depth > 0 и RMS < 2 с, как в `compare_bul`):

|---|---|---|---|---|---|---|---|

Recall не меняется (координаты — `enrich`). Ошибки в сотни км остаются у перемешанных событий (например, май 10.05 00:47 через 1.5 мин после M4.7) — это вход, не таблица. **Ограничения:**
- Сетка и годограф — только Кавказ (NCAU). Для другого региона — свои `--ptt-grid` и `--tt-table` (`core/fit_traveltime.py --bul ...`).
- Глубина фиксирована (15 км) — для глубоких событий R от точки занижен.
- Годограф — первая P без разделения Pg/Pn, один на весь регион; разброс ±1.5–2 с покрывается допуском 2.5 с.
- Станции без координат (в StationXML и `--station-coords-json`) в локации не участвуют.

1. **Парсинг XML** (`parse_xml_full`) — для каждого `<event>` достаёт `publicID`, время очага (не используется в формуле, только для лога) и словари пиков `{station: datetime}` отдельно для P и S.
2. **Вычисление R** — по умолчанию (`--distance-source sp`) `compute_r_dict()` по S-P формуле выше; отбрасывает `R <= 0` и `R > --r-max-km`. При `--distance-source locator` — для событий с сошедшимся решением `core/locator.py` вместо этого `compute_r_dict_from_locator()` (реальная дистанция по координатам), с автоматическим откатом на `compute_r_dict()` для событий без решения (см. раздел выше).
3. **Загрузка станционных поправок** — если передан `--sta-corrections`, читает CSV в словарь `{station: S}`.
4. **Кэш амплитуд** (`--cache-amp`):
   - если файл существует и `--rebuild-cache` не передан — загружается как есть, шаги 5–6 пропускаются;
   - иначе выполняется полное извлечение амплитуд (см. ниже) и кэш перезаписывается.
5. **Извлечение амплитуд** (только при пересборке кэша) — см. отдельный раздел «Измерение амплитуды A» и «Параллелизация по станциям».
6. **Вычисление ML события** (`compute_event_ml_v2` для каждого `pub_id`) — см. «Многоступенчатая фильтрация».
7. **Статистика** (`print_distribution`) — перцентили ML (1–99), min/max, топ-3 самых маленьких и самых больших ML с `pub_id`.
8. Если передан `--diag-pubid` — построчная диагностика по станциям для этого события (см. ниже).
9. Если передан `--info` — работа заканчивается здесь, XML не изменяется.
10. **Фильтрация и запись XML** (`filter_xml`) — см. «Фильтрация XML». Валидация выходного файла в скрипт не встроена — выполняется отдельным ручным запуском `core/validate_associator_v2.py`.

## Измерение амплитуды A

### Индекс форм волн (`build_waveform_index`)

Перед чтением любых файлов строится индекс: для каждой станции — отсортированный по времени список файлов одного (!) компонента. Компонент выбирается **один раз на станцию**, по приоритету из `--comp-priority` (по умолчанию **E > N > Z**) — если для станции есть файлы первого по приоритету компонента, остальные для неё вообще не индексируются и не читаются ни для одного события. Компонент выбирается заранее для всей станции, а не под конкретное событие.

### Кластеризация и оконное чтение

Раз чтение MSEED — самая дорогая часть, события группируются перед чтением:

1. Для каждой станции все нужные S-времена (`(pub_id, sta, s_time)`) группируются по **файлу**, в который они попадают (`find_waveform_file` — простой поиск по границам `t_start <= t < t_end` в индексе).
2. Внутри одного файла триплеты разбиваются на **кластеры по времени** (`_split_triples_by_time`, `--max-group-span-sec`, по умолчанию 300с) — так, что события, случившиеся близко по времени (в пределах 5 минут), читаются одним вызовом `obspy_read()`, а не по разу на событие.
3. Для кластера читается окно `[min(S) − read_margin_sec, max(S) + win_sec + read_margin_sec]` (`--read-margin-sec`, по умолчанию 60с) — запас по краям нужен как контекст для `remove_response`/`detrend`/`taper` (без запаса на краях окна возникают артефакты). Реальный измерительный интервал `[S, S+win_sec]` вырезается (`tr.slice`) уже после снятия ответа.

### Снятие инструментального ответа и фильтрация

Для прочитанного окна (один раз на кластер, не на событие):

1. `detrend('linear')`, `taper(max_percentage=0.05, type='cosine')`.
2. `remove_response(inventory=inventory, output='DISP', pre_filt=(0.5, 1.0, nyq·0.85, nyq·0.95), water_level=60)` → смещение грунта в метрах. `nyq` — частота Найквиста по фактической частоте дискретизации трассы.
3. Если частота дискретизации трассы не входит в `{50, 80, 100, 200}` Гц (нестандартное значение из MSEED-заголовка) — она принудительно заменяется на `100.0` (если исходно `>75`) или `50.0` — тот же класс проблемы, что и правило №2 в `CLAUDE.md` («sampling_rate из attrs — всегда неверно»).
4. Если `--no-bandpass` не передан — полосовой фильтр `--bp-freqmin`–`--bp-freqmax` Гц (по умолчанию **1–5 Гц**, 4-й порядок, нулевая фаза). Без него микросейсмический шум 0.5–1 Гц завышает ML на 0.5–1.0 единицы — формула калибровалась на WA-эквивалентной полосе (T≈0.2–0.6с → f≈1.7–5 Гц).
5. Если `remove_response` падает с исключением (частая причина — рассинхрон между MSEED и StationXML) — амплитуда для всех событий этого кластера записывается как `None`, а не бросается ошибка на весь прогон.
6. Если `--metadata-dir` не указан или в нём нет ни одного StationXML — амплитуда не считается вообще (`None` для всех пар), это не аварийная ситуация, а осознанный режим (можно строить кэш поэтапно).

Максимум `|данные|` на срезе `[S, S+win_sec]` (`--win-sec`, по умолчанию 5с) → амплитуда в метрах → `×AMP_SCALE_NM (1e9)` → нм.

**Почему горизонтальная компонента:** приоритет `--comp-priority` (по умолчанию E > N > Z). S-волна максимальна на горизонталях. **Только S-волна** — амплитуда P-волны в этом модуле нигде не измеряется и в формулу не входит (формула Дягилева использует именно амплитуду S как энергетически наиболее показательную).

## Кэширование амплитуд

Кэш — CSV с колонками `pub_id,sta,A` (метры, не нм), хранится по пути `--cache-amp` (по умолчанию `workspace/magnitude/output/amps_filter_cache.csv`). При повторном запуске кэш подгружается целиком, MSEED не перечитывается вообще — вычисление ML и фильтрация XML занимают секунды. Пересборка — `--rebuild-cache`.

Кэш специфичен для набора событий во входном XML: при смене `--assoc-in` на XML с другими событиями кэш нужно пересобрать (иначе новые `pub_id` просто не найдутся в кэше и получат `A=None`). Смена `--ml-threshold`, `--sta-corrections`, `--exclude-stations`, коэффициентов формулы (`--ml-b-log`/`--ml-b-lin`/`--ml-c`) или порогов агрегации (`--n-min-sta`, `--ml-outlier-sigma`, `--a-nm-min`, `--a-max-nm`) пересборки **не требует** — это только постобработка уже закэшированных сырых амплитуд. Пересборка нужна, только если меняется то, что влияет на саму амплитуду до кэша: `--win-sec`, `--read-margin-sec`, `--max-group-span-sec`, `--no-bandpass`/`--bp-freqmin`/`--bp-freqmax`, `--comp-priority`, `--metadata-dir`, `--waveforms`.

## Многоступенчатая фильтрация ML для одного события

Для каждого события собирается набор оценок от разных станций. Задача — получить одно надёжное число ML из этого набора, отбросив плохие измерения. Этим занимается `compute_event_ml_v2` — единственный путь агрегации в `v5` (в `v4` он тоже был единственным рабочим путём, legacy ratio-фильтр в `v5` удалён совсем, см. «Отличие от `ml_filter_v4.py`»).

### Что вычисляется на каждой станции

Для станции `i` с расстоянием `R_i` (км) и амплитудой `A_i` (нм):

```
ML_i = lg(A_i) + b_log·lg(R_i) + b_lin·R_i + c + S_i
```

Формула инвертирует зависимость от расстояния и оставляет только вклад источника. В идеале все `ML_i` по разным станциям должны совпадать. На практике они расходятся из-за разной геологии под станцией, помех на конкретной записи, ошибок пика P или S, рефракции и анизотропии среды.

### Шаг 1: Физические отсечки (`_ml_entries`)

До статистики отбрасываются физически невалидные точки:

| Условие | Флаг/значение | Причина |
|---|---|---|
| `sta in --exclude-stations` | — | станция явно исключена пользователем |
| `R < --r-min-km` | по умолчанию 20 км | near-source, формула нелинейна |
| `A` отсутствует или `<= 0` | — | не удалось измерить (см. «Измерение амплитуды») |
| `A < --a-nm-min` | по умолчанию 0.005 нм | ниже уровня шума, артефакт `remove_response` |
| `A > --a-max-nm` | по умолчанию 1e6 нм | физически невозможно (>1 мм), сбой обработки |

(`R > --r-max-km` — отсекается раньше, ещё на шаге `compute_r_dict`, до входа в `_ml_entries`.)

После этого остаётся список `entries = [(sta, R_i, A_i, ML_i), ...]`.

### Шаг 2: минимум станций

Если `len(entries) < --n-min-sta` (по умолчанию 4) — ML для события не считается (`None, 0`). Лучше не иметь оценки, чем иметь её по 1–3 станциям.

### Шаг 3: σ-фильтр выбросов (`_filter_by_sigma_v2`)

**Вычисление центра:**
```
M_med = median(ML_1, ML_2, ..., ML_N)
```
Медиана, а не среднее — потому что она устойчива к выбросам. Если одна станция даёт ML=5.0 при остальных ML≈1.5, среднее сдвинется к 2.0, медиана останется на 1.5.

**Вычисление разброса:**
```
σ = std(ML_1, ML_2, ..., ML_N)
```
Если `σ == 0` (все станции дали идентичный ML) — фильтр не применяется, берутся все станции как есть.

**Порог и проверка каждой станции:**
```
thr = --ml-outlier-sigma · σ   (по умолчанию 1.5)

|ML_i − M_med| ≤ thr  →  станция остаётся
|ML_i − M_med| > thr  →  станция-выброс, отбрасывается
```

**Пример** с 6 станциями (дефолт `--ml-outlier-sigma 1.5`):

| Станция | R, км | ML_i | |
|---------|-------|------|-|
| BEYR    | 45    | 1.42 | |
| DOMR    | 67    | 1.51 | |
| GOYR    | 89    | 1.48 | |
| SHA1    | 112   | 1.55 | |
| MRNR    | 134   | 1.61 | |
| NEUR    | 158   | 3.20 | ← плохой пик |

```
M_med = median([1.42, 1.51, 1.48, 1.55, 1.61, 3.20]) = 1.53
σ     = std([...]) = 0.63
thr   = 1.5 · 0.63 = 0.94

BEYR:  |1.42 − 1.53| = 0.11 ≤ 0.94  →  OK
DOMR:  |1.51 − 1.53| = 0.02 ≤ 0.94  →  OK
GOYR:  |1.48 − 1.53| = 0.05 ≤ 0.94  →  OK
SHA1:  |1.55 − 1.53| = 0.02 ≤ 0.94  →  OK
MRNR:  |1.61 − 1.53| = 0.08 ≤ 0.94  →  OK
NEUR:  |3.20 − 1.53| = 1.67 > 0.94  →  ВЫБРОС
```

**Защита от деградации:** если после удаления выбросов осталось меньше `--n-min-sta` станций — фильтрация отменяется, возвращается исходный список (включая «выброс» — вычислять ML всё равно лучше, чем не вычислять).

**Почему 1.5σ по умолчанию, а не 2σ или 3σ:**

| Порог | Поведение |
|-------|-----------|
| 3σ    | слишком мягкий — явные выбросы проходят |
| 2σ    | стандартный статистический, но при малых сетях (4–6 станций) σ сама нестабильна |
| **1.5σ (дефолт)** | умеренно строгий: убирает станции с отклонением >1.5σ от разброса сети, оставляет нормальные флуктуации |

При типичном разбросе ML по станциям σ≈0.3–0.5 порог составляет 0.45–0.75 единиц магнитуды — это физически разумно. Значение настраивается через `--ml-outlier-sigma`.

### Шаг 4: Финальная оценка

```
ML_события = mean(ML_i по оставшимся станциям)
```

Среднее (а не медиана) — потому что после σ-фильтрации выбросов уже нет, оставшиеся `ML_i` близки друг к другу. Среднее тогда точнее медианы (меньше дисперсия при симметричном распределении).

### Итоговая схема

```
entries (N станций с ML_i)
        │
        ▼
[физические отсечки] → убираем excluded, R<r_min, A отсутствует/<=0, A<a_nm_min, A>a_max_nm
        │
        ▼
   N < n_min_sta ?  →  ML = None (нет оценки)
        │
        ▼
  M_med = median(ML_i)
  σ     = std(ML_i)
  thr   = ml_outlier_sigma·σ
        │
        ▼
  убираем |ML_i − M_med| > thr
        │
        ▼
   N < n_min_sta ?  →  откат, берём все (до фильтра)
        │
        ▼
  ML_события = mean(ML_i по оставшимся)
```

```
Станция    R,км       A,нм    ML_sta   Статус
--------------------------------------------------------------
BEYR       45.2      812.30     1.42   OK
DOMR       67.1      654.11     1.51   OK
NEUR      158.3     9800.00     3.20   |δ|=1.67>1.5σ=0.94
KRNR       12.0        —          —    R<20км
```

`Статус` показывает, почему станция вошла или не вошла в финальную оценку: `OK` — учтена; `R<Nкм` — ниже нижней границы применимости формулы (`--r-min-km`); `нет ответа` — `remove_response` не сработал; `A=0` / `A>A_MAX` — амплитуда невалидна; `|δ|=...>Xσ=...` — отброшена σ-фильтром, где `X` — реально переданный `--ml-outlier-sigma` (в `v4` эта метка была хардкодом `2σ` независимо от фактического множителя — поправлено в `v5`).

## Фильтрация XML и имя выходного файла

`filter_xml` копирует дерево (`copy.deepcopy`), затем для каждого `<event>`:
- нет оценки ML и `--keep-no-ml` не передан → событие удаляется (это поведение по умолчанию);
- нет оценки ML и `--keep-no-ml` передан → событие остаётся;
- `ML >= --ml-threshold` → остаётся;
- `ML < --ml-threshold` → удаляется.

Если `--assoc-out` не задан, имя выходного файла строится автоматически рядом с `--assoc-in`:
```
associations_ml<tag>.xml,  tag = f"{thr:.1f}" с заменой '-' → 'm' и '.' → 'p'
```
Например, порог `1.5` → `associations_ml1p5.xml`, порог `-0.5` → `associations_mlm0p5.xml`.

В конце печатается сводка: сколько событий было во входном XML, сколько сохранено (с разбивкой сколько из них — без оценки ML, если `--keep-no-ml`), сколько удалено (с разбивкой по «без оценки ML» среди удалённых).

## Интеграция с `--sta-corrections`

CSV с колонками `station,S` (либо `station,correction` — читается любое из двух имён). Обычно это выход `core/sta_correction_estimator.py` (`--out-summary`). Поправка `S` прибавляется к ML каждой станции ещё на шаге вычисления `ML_i` (см. формулу выше) — то есть до σ-фильтра, поэтому поправка может как приблизить, так и, в редких случаях, наоборот вывести станцию за порог выброса.

## Валидация результата (отдельный шаг, не часть скрипта)

`ml_filter_v5.py` валидацию не запускает — реальный рабочий процесс: пользователь всегда проверяет результат отдельным ручным запуском `core/validate_associator_v2.py` на только что записанном `associations_ml<tag>.xml`.

## Параллелизация по станциям

Станции (не события!) делятся round-robin на `--workers` (по умолчанию 4) групп. Каждый поток (`ThreadPoolExecutor`) работает только со своим набором станций — нет конкуренции за файлы, нет блокировок между потоками. Внутри потока события уже сгруппированы по файлу и кластеризованы по времени (см. «Измерение амплитуды A»), чтобы читать один файл одним вызовом `obspy_read`. После каждой группы станций вызывается `gc.collect()`.

## Известные ограничения

- Индекс волн выбирает компонент **один раз на станцию** по всем доступным файлам — если для станции физически существуют файлы двух компонент с разными периодами покрытия (например, часть месяца писалась только Z), периоды, покрытые исключительно компонентом ниже по приоритету, будут пропущены, а не подхвачены как fallback.
- **Один `--cache-amp` на один `associations.xml`.** Существующий кэш загружается как есть, амплитуды для событий, которых в нём нет, **не досчитываются**. `pub_id` ассоциатора — случайные UUID, разные при каждом прогоне, даже на тех же детекциях. Если подать XML нового прогона ассоциатора со старым кэшем, все события останутся без амплитуд: «Событий с оценкой ML: 0», выход пустой, без ошибки. Для каждого прогона ассоциатора нужен свой файл кэша (или `--rebuild-cache`). Наткнулись 2026-10-09.
- Кэш амплитуд ключуется по `(pub_id, sta)` без привязки к параметрам, влияющим на саму амплитуду (`--no-bandpass`, `--bp-freqmin/max`, `--win-sec`, `--comp-priority` и т.д.) — если один из них меняется между запусками с одним и тем же `--cache-amp`, кэш всё равно применяется как есть (пересборка не форсируется автоматически, нужен `--rebuild-cache` вручную; см. «Кэширование амплитуд» — какие параметры требуют пересборки, а какие нет).
- `--exclude-stations` исключает станцию только из агрегации ML события, но не из диагностического вывода `--diag-pubid` — там она видна без пометки причины исключения (текущая реализация не различает «excluded» в статусной колонке, это визуально совпадёт с обычным `OK`/выбросом по данным без явной пометки «excluded»).
