# associator.py — описание алгоритма

## Цель

Объединяет CSV-детекции всех станций (выход детектора, по одному файлу на станцию) в сетевые события: сначала готовит per-станционный «стейджинг» (фильтрует детекции по порогам вероятности/SNR/неопределённости, опционально переписывает вероятности с учётом MC Dropout), затем запускает сам ассоциатор (`run_associator_v2` из `EQTransformer/utils/associator.py`) — скользящее окно по времени P-пиков с проверкой физической согласованности между станциями. На выходе — QuakeML (`associations.xml`), файл фаз в формате hypoInverse (`Y2000.phs`) и словарь имён трасс по событию (`traceNmae_dic.json`).

**CLI есть (2026-09-06, `production-plan.md` Трек 1)** — все параметры (пути, список станций, пороги, параметры окна) задаются флагами (`--help`); константы в начале файла остались как значения по умолчанию. Предыдущая версия без CLI — `legacy/associator_v3.py` (не `associator_v1.py`/`associator_v2.py` — те заняты другим смыслом, см. `legacy/README.md`). До этой ревизии весь код выполнялся построчно на верхнем уровне модуля (без функции, без `if __name__ == "__main__"`) — теперь обёрнут в `run_associator()`, вызываемую из CLI-обвязки; `_passes`/`_passes_v2`/`prepare_station` принимают пороги как параметры функций, а не читают глобальные константы напрямую. Алгоритм не менялся.

## Конфигурация — CLI-флаги (`--help`)

Константы с теми же именами остались в файле как значения по умолчанию.

| Флаг | Константа-дефолт | Назначение |
|---|---|---|
| `--source-dir` | `SOURCE_DIR` | откуда брать сырые CSV детекций по станциям (`{source-dir}/{STATION}/{station}.csv` — формат, который пишет `core/detector.py`/`process_station_v3`) |
| `--input-dir` | `INPUT_DIR` | куда пишется отфильтрованный стейджинг (`{input-dir}/{STATION}/X_prediction_results.csv` — формат, который читает `run_associator_v2`) |
| `--output-dir` | `OUTPUT_DIR` | куда пишет результат сам ассоциатор (`associations.xml`, `Y2000.phs`, `traceNmae_dic.json`) |
| `--stations` | `STATIONS` (строка кодов через запятую) | список кодов станций, участвующих в этом прогоне ассоциации |
| `--det-thr` / `--p-thr` / `--s-thr` | `DET_THR` / `P_THR` / `S_THR` | пороги вероятности: детекция в целом / P-пик / S-пик, ниже которых пик считается отсутствующим |
| `--keep-ps` (`--no-keep-ps`) | `KEEP_PS` | включено — строка проходит стейджинг только если есть **и** P, **и** S пик (AND); выключено (по умолчанию) — достаточно хотя бы одного (OR) |
| `--p-snr-thr` / `--s-snr-thr` | `P_SNR_THR` / `S_SNR_THR` | минимальный SNR пика, чтобы засчитать его как валидный; `0.0` — проверка отключена (пик принимается по одной только вероятности) |
| `--uncertainty-mode` | `UNCERTAINTY_MODE` | как учитывать MC Dropout-неопределённость пиков при стейджинге — `none`/`filter`/`weight` (см. ниже) |
| `--start-time` / `--end-time` | `START_TIME` / `END_TIME` | границы временного диапазона, который передаётся в `run_associator_v2` (строки `'YYYY-MM-DD HH:MM:SS.fff'`) |
| `--moving-window` / `--pair-n` / `--coherence-tolerance` | `MOVING_WINDOW` / `PAIR_N` / `COHERENCE_TOLERANCE` | параметры самого ассоциатора — см. раздел про `run_associator_v2` |

`consider_combination` — не CLI-флаг: `_dbs_associator_v2` бросает `ValueError` при `True` (не поддерживает эту комбинацию, см. ниже), поэтому фиксирован как `False` в самом вызове, а не вынесен в конфигурацию.

## Шаг 1 — Стейджинг: фильтрация и (опционально) взвешивание детекций

Перед запуском ассоциатора скрипт сам готовит входные CSV — это не тонкая обёртка вокруг `run_associator_v2`, а отдельный, содержательный этап:

1. **Очистка устаревшего стейджинга.** Если в `INPUT_DIR` есть подпапки станций, которых нет в текущем `STATIONS`, они удаляются (`shutil.rmtree`) — иначе `run_associator_v2` подхватил бы данные станций, исключённых из текущего прогона (он сам читает все подпапки `INPUT_DIR`, а не только те, что перечислены в `STATIONS`).
2. **Для каждой станции из `STATIONS`:** если исходный CSV (`{SOURCE_DIR}/{ST}/{st}.csv`) существует, каждая строка (детекция) проходит через `prepare_station()` → `_passes()`/`_passes_v2()` → (опционально) `_apply_weight()`, результат построчно пишется в `{INPUT_DIR}/{ST}/X_prediction_results.csv`.

### Фильтр по порогам (`_passes` / `_passes_v2`)

Обе функции реализуют одну и ту же логику принятия/отклонения строки, различаясь только тем, к какой вероятности применяются пороги:

- `_passes` — к **сырой** вероятности (`detection_probability`, `p_probability`, `s_probability` как есть).
- `_passes_v2` — к **эффективной** вероятности `p_prob × (1 − p_unc)` (`_eff_prob`) — то есть неопределённость снижает эффективную вероятность пика перед сравнением с порогом.

Логика (общая для обеих): пик P засчитан, если `p_arrival_time` не пусто и вероятность (сырая либо эффективная — в зависимости от функции) `>= P_THR`, и если `P_SNR_THR > 0`, дополнительно `p_snr >= P_SNR_THR`. Аналогично для S. Строка (детекция) проходит стейджинг, если `detection_probability >= DET_THR` **и** (`has_p AND has_s`, если `KEEP_PS=True`, иначе `has_p OR has_s`).

### Режимы учёта неопределённости (`UNCERTAINTY_MODE`)

| Режим | Какой фильтр применяется | Что записывается в стейджинг-CSV |
|---|---|---|
| `'none'` | `_passes` (по сырой вероятности) | вероятности как есть |
| `'weight'` | `_passes` (по сырой вероятности — неопределённость на прохождение фильтра не влияет) | вероятности **переписываются** на эффективные (`_apply_weight`: `prob → prob × (1 − unc)` для `detection_probability`, `p_probability`, `s_probability`) — сам порог применяется к сырому значению, но дальше по цепочке (в `run_associator_v2`, при взвешивании фаз в `Y2000.phs`) уже используются взвешенные вероятности |
| `'filter'` | `_passes_v2` (по эффективной вероятности) | вероятности как есть (не переписываются) |

Иначе говоря: `'weight'` смягчает то, что видит ассоциатор дальше по цепочке (веса фаз), не меняя, какие детекции вообще проходят стейджинг; `'filter'` — наоборот, меняет именно то, что проходит стейджинг (пик с высокой неопределённостью может быть отброшен даже при высокой сырой вероятности), но передаёт дальше исходные числа. `'none'` — оба механизма отключены, неопределённость целиком игнорируется (поведение до появления MC Dropout).

## Шаг 2 — `run_associator_v2` (в `EQTransformer/utils/associator.py`)

Готовый стейджинг (`INPUT_DIR`) передаётся в `run_associator_v2(input_dir, start_time, end_time, moving_window, pair_n, output_dir, consider_combination, coherence_tolerance)`.

1. Каждый файл `{STATION}/X_prediction_results.csv` построчно парсится (`_pick_database_maker`) и загружается во временную SQLite-базу с фиксированным именем **`phase_dataset`** — файл создаётся в **текущей рабочей директории** (`os.path.exists("phase_dataset")` / `sqlite3.connect("phase_dataset")` — путь не абсолютный и не строится от `_ROOT`, в отличие от всех остальных путей в проекте). Существующий файл с этим именем удаляется перед созданием новой базы. ⚠️ Если запускать из разных рабочих директорий, файл `phase_dataset` будет создаваться в разных местах — это единственный путь в связке `associator.py`/`run_associator_v2`, который не абсолютный.
2. Таблица читается обратно как `pandas.DataFrame`, столбцы времени парсятся в `datetime`.
3. Вызывается `_dbs_associator_v2` — собственно алгоритм ассоциации, четыре фазы:

### Фаза 1 — скользящее окно по `p_arrival_time`

В отличие от `run_associator` (v1, группировка по `event_start_time`, соседний блок в том же модуле — начало 60-секундного окна детекции, а не физическое время P-пика; страдает от «проблемы границы корзины»: одно и то же землетрясение на разных станциях может дать `event_start_time` в разных 60-секундных бинах и никогда не набрать `pair_n` совпадений), `run_associator_v2` группирует **по времени P-пика** и использует скользящее окно с шагом `step = moving_window // 2`, а не неперекрывающиеся интервалы — так события гарантированно попадают целиком хотя бы в одно окно.

Реализовано эффективно: все `p_arrival_time` переводятся в смещения в секундах от `start_time` и сортируются; для каждого положения окна `np.searchsorted` находит границы `[lo, hi)` за `O(log N)`, а не полный проход по таблице. Внутри окна для каждой станции оставляется только детекция с максимальной `detection_prob` (`drop_duplicates('station')` после сортировки по убыванию вероятности) — то есть один кандидат-событие описывается не более чем одной строкой на станцию. Если уникальных станций в окне `>= pair_n` — окно превращается в кандидата события.

### Фаза 2 — дедупликация перекрывающихся окон

Поскольку окна перекрываются (шаг = половина ширины), одно и то же землетрясение почти всегда порождает несколько кандидатов подряд. Два кандидата считаются одним и тем же событием и объединяются, если время между ними `<= step` **и** они разделяют не менее `max(2, pair_n − 1)` общих станций — тогда берётся объединение станций с лучшей (по вероятности) детекцией на станцию.

### Фаза 3 — фильтр физической согласованности (`_coherent_subset`)

Для каждого кандидата проверяется, что все пары станций физически совместимы: разница P-времён между станциями `A` и `B` не должна превышать `dist(A, B) / Vp + coherence_tolerance` (по сути неравенство треугольника для скорости распространения P-волны). Если есть нарушения — итеративно удаляется станция с наибольшим числом нарушений (при равенстве — с меньшей `detection_prob`), пока оставшееся подмножество не станет полностью согласованным или пока станций не станет меньше `pair_n` (тогда кандидат отбрасывается целиком — `None`). `Vp` фиксирован внутри функции (`6.0` км/с), настраивается только `coherence_tolerance` (передаётся из `associator.py`).

### Фаза 4 — запись результата

Для каждого прошедшего фильтры кандидата: строка гипоцентра в `Y2000.phs` (в качестве lat/lon/depth используются координаты **первой станции** кандидата — не настоящая локация, а плейсхолдер для формата; правило проекта — гипоцентр в этом пайплайне нигде не вычисляется, см. `core/export_bul.py`) + по одной строке P/S-фазы на станцию (вес фазы — `_weighcalculator_prob`, дискретизация вероятности в 0–4 по фиксированным порогам, с учётом `p_unc`/`s_unc`, если есть) + `Event`/`Origin`/`Pick` в QuakeML-каталог (`obspy.core.event.Catalog`). Время очага в QuakeML = `min(p_arrival_time)` среди подтверждённых станций.

Если внутри окна на одну станцию неожиданно попало больше одной строки после дедупликации (`row_buffer`) — это не потерянные данные: при `len(row_buffer) >= 2*pair_n` они записываются как **второе, отдельное событие** (второй блок в `Y2000.phs`, отдельная запись в `traceNmae_dic.json`, но **не** отдельный `Event` в QuakeML-каталоге — `cat.append(event)` вызывается только один раз на исходного кандидата); иначе они просто попадают в `traceNmae_dic.json` под служебным `evidd`-ключом, не в основной каталог. Это унаследовано от `_dbs_associator` (v1) без изменений в v2.

`consider_combination=True` в `_dbs_associator_v2` не поддерживается — функция сразу бросает `ValueError` («используйте `_dbs_associator`»); `core/associator.py` всегда вызывает `run_associator_v2` с `consider_combination=False`.

## Выходные файлы

- **`associations.xml`** — QuakeML-каталог событий (по одному `Event`/`Origin`/`Pick*` на событие).
- **`Y2000.phs`** — тот же результат в формате фаз hypoInverse (одна гипоцентровая строка + строки фаз на событие); формат, который принимают внешние локаторы.
- **`traceNmae_dic.json`** — словарь `{event_id: [имена_трасс]}` — какие конкретно детекции (по имени трассы `traceID*station*event_start_time`) вошли в событие; нужен, если потом требуется вытащить исходные записи для кросс-корреляции при релокации.

## Известные особенности (не зависят от текущих значений констант)

- `phase_dataset` — временная SQLite-база, создаётся/удаляется по **относительному** имени файла (от текущей рабочей директории запуска, не от `_ROOT`) — единственное некорректное с точки зрения конвенции проекта место в этой цепочке; при параллельном запуске нескольких ассоциаций из одной рабочей директории один прогон удалит базу другого.
- `_coherent_subset` — при обнаружении нарушений полный перебор всех пар станций на каждой итерации удаления (`O(n²)` на итерацию); для типичных размеров события (несколько–десяток станций) не критично, но не рассчитан на сотни станций в одном окне.
- Один «кандидат» после дедупликации может дать **два** события в `Y2000.phs`/`traceNmae_dic.json` (основное + `row_buffer`-переполнение), но только **один** `Event` в `associations.xml` — при сверке числа событий по разным выходным файлам это стоит иметь в виду.
- `_dbs_associator_v2` не умеет `consider_combination=True` (в отличие от v1) — жёстко ограничение, не настройка.
