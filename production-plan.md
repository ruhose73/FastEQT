### Ключевые решения этой сессии и почему (не самоочевидны, стоит помнить)
- **Конфиг-файлов не будет** в этом заходе — по решению пользователя сначала весь `core/` становится CLI-управляемым без исключений, формат конфига (YAML/TOML/JSON, приоритет CLI>конфиг>дефолт) — отдельная будущая задача, не проектировалась.
- **Список станций — явный флаг `--stations STA1,STA2,...`, не автосканирование директории.** Рассматривался вариант авто-обнаружения (по образцу уже работающего `sta_correction_estimator.py`, который сканирует `station_*.json`) — **пользователь отклонил**, предпочёл явную передачу списка через запятую (дефолт = сегодняшний хардкод-список).
- **Диапазон дат унифицирован на `--date-from`/`--date-to`** для `cpu_pipeline.py` (раньше только месяц/год) и `gpu_pipeline.py` (уже был произвольный диапазон) — выбран более общий вариант для обоих.
- **Правки — не на месте, а в новых файлах**, потому что пользователь пока не может закоммитить репозиторий и ему нужна точка отката. Итоговая схема (первая идея — суффикс `_cli` рядом с оригиналом — заменена на более простую): текущий файл переносится в `legacy/` **под тем же именем** через `git mv` (полноценный git-бэкап с историей, не просто копия на диске), а в `core/` под старым именем создаётся новая версия. Побочный плюс: `cpu_pipeline.py`/`gpu_pipeline.py` грузят `detector.py` через `importlib` по имени файла в той же папке — раз имя не поменялось, ссылку чинить не пришлось.
  - Наименование бэкапов в `legacy/` пришлось решать по ходу: `legacy/associator.py`/`associator_v1.py`/`associator_v2.py` уже заняты — и означают не то, что интуитивно ожидалось бы от такой нумерации (`_v1` — это побайтовый бэкап сегодняшнего `associator.py`, `_v2` — не следующая по времени, а более старая версия). Бэкап `core/associator.py` до перехода на CLI назвали `legacy/associator_v3.py`.
- **`detector.py`: пороги предиктора подняты в CLI, а не только пути/список станций.** `detection_threshold`/`P_threshold`/`S_threshold`/`keepPS`/`allowonlyS`/`spLimit`/`batch_size` раньше были зашиты прямо в телах `worker_v3`/`worker_v4` — не были даже параметрами функций. Теперь — параметры по всей цепочке `process_station_v3 → preproc_sequential_v5 → worker_v4`, доступны как флаги в `detector.py`/`cpu_pipeline.py`/`gpu_pipeline.py`. `EQTransformer/` не тронут (правило №1 `CLAUDE.md`) — там сигнатуры это уже принимали.
- **Найден и исправлен реальный баг при переходе (не было в плане заранее):** `python core/detector.py --help` падал на импорте `EQTransformer` — при прямом запуске скрипта `sys.path[0]` = папка `core/`, не корень проекта, поэтому вместо локальной пропатченной `EQTransformer/` подхватывался установленный через pip пакет `eqtransformer==0.1.61` из `site-packages`. Добавлен `sys.path.insert(0, _ROOT)`, как уже было в `associator.py`.
- **`associator.py` — не только CLI, но и структурная правка.** До этой сессии весь код исполнялся построчно на верхнем уровне модуля (без функции, без `if __name__ == "__main__"`) — обёрнут в `run_associator()`.

## Трек 2 — Полностью автоматический realtime-пайплайн

### Цель
Оркестратор, который сам, без ручного вмешательства: забирает новые данные из архива → прогоняет через `data_processors/` (конвертация SEED-имён, метаданные) → передаёт в детектор → передаёт результат в ассоциатор. Пригоден для запуска в реальном времени (по расписанию/непрерывно), а не только для разовых батчевых прогонов текущими скриптами.

Судя по формулировке задачи, границы автоматического пайплайна — **от сырого архива до выхода ассоциатора** (`associations.xml`). ML-фильтрация/валидация/экспорт бюллетеня (`ml_filter_v4.py`/`validate_associator_v2.py`/`export_bul.py`) в эту границу явно не включены пользователем — уточнить, должны ли они тоже стать частью автоматической цепочки, или остаются отдельным, запускаемым вручную шагом поверх результатов оркестратора.

### 2.1 — Вопросы, которые нужно закрыть до проектирования (архитектурные развилки)

1. **Что значит "новые данные" технически** — архив (`SDS`) пополняется новыми файлами того же дня (дозапись) или только целыми новыми сутками? От этого зависит, можно ли обрабатывать день сразу после полуночи или нужно ждать закрытия файла.
2. **Отслеживание состояния** — что уже обработано, а что нет. Нужен явный стейт (файл/БД с отметкой "по эту дату станция X обработана"), иначе повторный запуск либо пересчитывает всё заново, либо пропускает новое. Сейчас в пайплайне такого учёта нет — `data_processors/geofile_processor.py` просто копирует файлы по диапазону дат, `detector.py`/pipeline-обёртки берут диапазон дат константой.
3. **Гранулярность запуска** — раз в сутки (после закрытия суточного файла) или чаще (внутрисуточные довороты по мере поступления)? Сильно влияет на то, как переиспользовать генератор сегментов (`geofile_splitter_multi_chanels_v3`), который сейчас ожидает целые сутки на входе.
4. **Что делать со станциями без данных / с опозданием** — ждать все станции перед запуском ассоциатора или запускать с тем, что есть, и потом дозапускать повторно (риск: `core/associator.py` сейчас пишет staging заново при каждом запуске и требует полный список станций).
5. **Ошибки и мониторинг** — что происходит, если детектор упал на одной станции (сейчас пайплайн это переживает — ошибка логируется, остальные станции продолжают), но нужно решить: нужен ли алертинг (письмо/сообщение) при сбое в автоматическом режиме, раз человека рядом с терминалом не будет.
6. **Где границы одного "прогона"** — один вызов оркестратора = один день? Один месяц? Скользящее окно (последние N дней) для случаев, когда станция прислала данные с опозданием?

### 2.2 — Из чего строить (что уже есть, что нужно добавить)

Уже есть, переиспользуется как шаг:
- `data_processors/geofile_processor.py`/`metadata_processor.py` — конвертация имён файлов и метаданных (сейчас: диапазон дат — константы в начале файла, тоже кандидат на параметризацию, см. Трек 1).

- Механизм отслеживания состояния «что уже обработано» (см. 2.1 п.2).
